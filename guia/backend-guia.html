03

Cómo corre tu código

Lo que pasa entre "escribo un archivo de texto" y "hay un programa atendiendo peticiones". Sin esto, todo lo demás son cajas mágicas.

Compilado  ·  interpretado  ·  máquina virtual  ·  JIT

Compilado (Go, Rust, C): un programa traduce todo tu código a instrucciones de la máquina antes de ejecutar, y produce un binario. Arranca rápido, corre rápido. Interpretado (Python, Ruby, JS clásico): otro programa —el intérprete— lee y ejecuta tu código línea por línea cada vez. Más lento, más flexible. Máquina virtual (Java, C#): tu código se compila a un formato intermedio (bytecode) que corre sobre una VM (la JVM, el CLR). JIT (just-in-time): la VM detecta el código que más se usa y lo compila a máquina en caliente — lo mejor de ambos mundos, tras un calentamiento.

Por qué importa Explica por qué Go arranca en milisegundos y un Spring Boot clásico tarda segundos, por qué un binario Rust no necesita que instales "el runtime", y por qué Python es cómodo para scripts pero se queda corto en cálculo intensivo.

Proceso  vs  hilo · thread

Un proceso es un programa en ejecución con su propia memoria aislada; el sistema operativo no deja que uno lea la memoria de otro. Un hilo es una línea de ejecución dentro de un proceso; varios hilos del mismo proceso comparten memoria. Crear un proceso es caro; crear un hilo es barato; cambiar entre ellos (context switch) siempre cuesta.

Cómo lo usan los servidores Unos usan varios procesos (PHP-FPM, Gunicorn con workers), otros varios hilos (Java), otros un solo hilo con un bucle de eventos que nunca se bloquea (Node.js), y otros "hilos verdes" livianísimos gestionados por el runtime, no por el OS (goroutines de Go, procesos de Elixir).

Concurrencia  vs  paralelismo

Concurrencia = estructurar el programa para manejar muchas tareas que progresan intercaladas (un cocinero alternando entre tres ollas). Paralelismo = ejecutar varias de verdad al mismo tiempo, en varios núcleos (tres cocineros). Puedes tener concurrencia sin paralelismo (un solo núcleo repartiendo su tiempo).

Primitivas de sincronización · lock, mutex, semáforo

Cuando dos hilos tocan el mismo dato a la vez, el resultado puede quedar corrupto (condición de carrera). Un mutex ("exclusión mutua") es un candado: solo un hilo lo tiene a la vez, el resto espera. Un semáforo permite hasta N a la vez (por ejemplo "máximo 10 conexiones a la base"). Abusar de candados los serializa a todos (matas el rendimiento) o crea un deadlock: dos hilos esperándose mutuamente para siempre.

La alternativa Modelos que evitan compartir memoria: pasar mensajes entre actores (Elixir), o canales (Go: "no te comuniques compartiendo memoria; comparte memoria comunicándote").

Bucle de eventos · event loop

El modelo de Node.js y de todo lo async de un solo hilo. Hay un bucle que va tomando tareas de una cola. Cuando una tarea pide algo lento (leer un archivo, la red), no espera: registra "cuando esto termine, ejecuta esta función (callback)" y sigue con la siguiente. El sistema operativo avisa al terminar, y el callback vuelve a la cola.

La trampa Si una tarea hace un cálculo pesado sin ceder el control, bloquea el bucle entero y nadie más es atendido. Por eso en Node el trabajo intensivo va a un hilo aparte (worker).

Qué pasa cuando escribes una URL

1. DNS "api.midominio.com" → 34.120.5.8 (resolución de nombre) 2. TCP apretón de manos de 3 pasos con esa IP en el puerto 443 3. TLS negociación de cifrado + verificación del certificado → canal seguro 4. HTTP el cliente envía: GET /pedidos/42 + cabeceras 5. Servidor router → middleware → handler → consulta a la base → respuesta 6. HTTP el servidor devuelve: 200 OK + cuerpo JSON 7. La conexión se reutiliza (keep-alive) o se cierra

Por qué saberlo Cada uno de esos pasos es un lugar donde algo puede fallar o ir lento (DNS mal configurado, certificado vencido, handshake lento, conexión no reutilizada). Depurar producción es saber en cuál de los siete estás.

HTTP a fondo

Es un protocolo de texto de petición-respuesta. Una petición tiene método (GET, POST, PUT, PATCH, DELETE), ruta, cabeceras (metadatos: quién soy, qué formato acepto, autenticación) y a veces cuerpo. La respuesta trae un código de estado: 2xx éxito, 3xx redirección, 4xx error del cliente (400 mal formado, 401 sin autenticar, 403 sin permiso, 404 no existe, 429 demasiadas peticiones), 5xx error del servidor. HTTP es sin estado: el servidor no recuerda peticiones anteriores por sí solo; para eso están cookies y tokens.

Idempotencia de los métodos

GET, PUT y DELETE son idempotentes: repetir la misma petición deja el sistema en el mismo estado. POST no lo es (dos POST = dos recursos creados). Importa porque en redes las peticiones se pierden y se reintentan; un cobro debe diseñarse para que reintentarlo no cobre dos veces (con una clave de idempotencia).

Las capas de un sistema

"Capa" se usa para cosas muy distintas y se mezclan todo el tiempo. Aquí van cinco mapas por niveles. Cada uno sirve para depurar un tipo de problema: cuando algo falla, primero nombras la capa, después tocas.

1 · La pila de ejecución · del transistor a tu configuración

Todo lo que hay entre el silicio y tu archivo de texto. Cada nivel le ofrece al de arriba una interfaz estable y le esconde su complejidad.

Configuración / variables de entorno Tu código Framework y librerías Runtime del lenguaje (V8/Node, CPython, la JVM, el runtime de Go) Librerías del sistema (libc, OpenSSL) Llamadas al sistema (syscalls: open, read, write, socket) Kernel del sistema operativo Controladores (drivers) Firmware / BIOS / UEFI CPU + juego de instrucciones (ISA: x86-64, ARM) Microarquitectura (cachés L1/L2/L3, pipeline, predicción de saltos) Compuertas lógicas Transistores

Para qué "El binario no arranca en el servidor" → librerías del sistema. "Va lento solo en producción" → normalmente kernel/disco o la capa de datos, casi nunca la microarquitectura. Un lenguaje compilado (Go, Rust) se salta el "runtime del lenguaje"; uno interpretado lo carga entero en cada arranque.

3 · Las capas de una aplicación · n-tier, Clean, hexagonal

Cómo divides tu código por responsabilidad. Las cuatro capas clásicas:

Presentación → controladores HTTP, serialización, validar la entrada Aplicación → casos de uso: "crear pedido" = orquestar varios pasos Dominio → reglas de negocio puras, entidades. NO sabe de HTTP ni de SQL Infraestructura → base de datos, colas, APIs externas, envío de email

La regla de oro (Clean Architecture, hexagonal, Onion — es el mismo tema con nombres distintos): las dependencias apuntan hacia adentro. El dominio no importa nada de infraestructura; la infraestructura implementa interfaces que define el dominio. Resultado: pruebas la lógica de negocio sin base de datos, y cambias PostgreSQL por otra cosa sin tocarla.

Señal de que está mal Si tu función que calcula el consolidado también abre la conexión a la base y arma el JSON de respuesta, tienes las tres capas pegadas. Extraer la lógica pura a su propio módulo es el refactor con mejor retorno.

4 · Las capas de infraestructura · el camino de una petición en producción

Navegador / app móvil │ CDN / edge → sirve estáticos, cachea, filtra bots │ Balanceador de carga → reparte entre servidores, termina el TLS │ API gateway (opcional) → autenticación, rate limit, enrutado │ Servidores de aplicación (varios, sin estado) │ Capa de caché (Redis) → sesiones, resultados calientes │ Base de datos (primaria + réplicas de lectura) │ Almacenamiento de objetos (S3) + backups

Y una capa ortogonal — dónde corre cada proceso: servidor físico → máquina virtual → contenedor → orquestador (Kubernetes). Cada nivel añade aislamiento y portabilidad a cambio de sobrecarga. Un proyecto chico vive feliz en "VM + contenedor" sin orquestador.

5 · Las capas de los datos · del byte al JSON

Bytes en el SSD Páginas / bloques Motor de almacenamiento (heap, árbol B, LSM-tree) Índices Modelo lógico (tablas, filas, columnas) Consulta SQL + plan de ejecución Driver de base de datos + pool de conexiones ORM / mapeo objeto-relacional Objetos de dominio DTO / esquema de respuesta JSON en la red

Para qué Cada salto es una traducción y un lugar donde se pierde rendimiento o correctitud: un ORM que genera N+1 consultas, una serialización que expone campos de más, un pool mal dimensionado. Depurar "la API va lenta" es recorrer esta lista hacia abajo.

La idea que une las cinco

Una capa ofrece una interfaz y esconde cómo lo hace. Eso te deja razonar sobre un nivel sin cargar con los de abajo — hasta que algo falla, y entonces la habilidad clave es localizar la capa antes de cambiar nada. El 90% de depurar es eso.

05

Conceptos del backend web

El vocabulario que hace que un framework tenga sentido. Cada uno resuelve un problema concreto: qué es, por qué existe, qué pasaría sin él.

Lenguaje  vs  librería  vs  framework

El lenguaje son las reglas (el idioma). Una librería es código ya hecho que tú llamas cuando lo necesitas. Un framework es una estructura que te llama a ti: él controla el flujo y ejecuta tus funciones en el momento correcto. El concepto se llama inversión de control.

Enrutamiento · routing

Una tabla que conecta cada URL + método con la función que la maneja. GET /usuarios/42 → verUsuario(42). Sin esto, tendrías un if gigante mirando la URL a mano.

Middleware

Funciones "en medio" del camino. La petición pasa por una fila de middlewares antes de tu lógica y la respuesta al salir. Sirve para lo que quieres en todas las peticiones: log, autenticación, límite de frecuencia, compresión, CORS.

petición → [log] → [auth] → [rate limit] → TU HANDLER ↓ respuesta ← [log] ← ← ← ← ← ← ← ← ← ← ← ← ← ← ┘

ORM y query builder

Los datos se piden con SQL. Un ORM mapea tabla ↔ clase, fila ↔ objeto: escribes Usuario.get(42) y genera el SQL. Un query builder es un punto medio: construyes la consulta con métodos (.where().join()) pero pensando en SQL, no en objetos. Django, Rails y Laravel traen ORM propio; con Go o Express eliges uno (Prisma, SQLAlchemy, GORM, Drizzle) o escribes SQL.

El costo del ORM Esconde lo que pasa: es fácil generar consultas lentas sin darte cuenta (el problema N+1: una consulta para la lista + una por cada elemento). Hay que saber leer el SQL que genera.

Validación  ·  serialización

Validar = verificar la forma de los datos que llegan antes de usarlos. Serializar = convertir un objeto en texto (JSON) para enviarlo; deserializar es lo inverso. FastAPI con Pydantic, o NestJS con class-validator, rechazan lo inválido automáticamente y devuelven un error claro.

Autenticación  ·  autorización

Autenticación: ¿quién eres? Autorización: ¿qué te dejo hacer? Dos mecanismos para recordar quién eres entre peticiones:

Sesión (cookie): al hacer login el servidor guarda tu sesión (en memoria, Redis o base) y te manda un identificador en una cookie. Cómodo para webs con navegador; el servidor recuerda estado. Token (JWT): el servidor te firma un token con tus datos dentro; lo mandas en cada petición y el servidor solo verifica la firma, sin recordar nada. Ideal para apps móviles y para escalar a muchos servidores.

Trampas del JWT No se pueden invalidar antes de que expiren (un logout no "borra" el token). No metas datos sensibles: el contenido es legible, solo va firmado, no cifrado. Expiración corta + un refresh token es el patrón habitual.

OAuth 2.0  ·  OpenID Connect

OAuth 2.0 es el protocolo de "iniciar sesión con Google/GitHub": delegas a un tercero la autenticación y recibes un token con permisos acotados, sin ver nunca la contraseña del usuario. OpenID Connect es una capa sobre OAuth que añade identidad ("este token corresponde a esta persona"). No implementes esto a mano: usa una librería o un proveedor (Auth0, Clerk, Keycloak, Supabase Auth).

Hashing de contraseñas

Nunca guardes contraseñas en texto. Se guarda un hash lento y con sal (un valor aleatorio por usuario que evita ataques con tablas precalculadas). Algoritmos correctos hoy: argon2, bcrypt, scrypt. Nunca MD5 ni SHA-256 a secas: son demasiado rápidos, un atacante prueba miles de millones por segundo.

Migraciones

Archivos con instrucciones de cambio a la base, versionados junto al código y aplicados en orden ("007: agrega columna teléfono"). Mantienen tu máquina, la de tus compañeros y producción sincronizadas. Herramientas: las de Django/Rails/Laravel, o Alembic, Flyway, golang-migrate.

Síncrono  vs  asíncrono

Cuando el servidor espera algo lento: síncrono se queda parado; asíncrono deja esa tarea en pausa y atiende otra. Importa cuando hay muchas conexiones que esperan mucho (chats, tiempo real, APIs que llaman APIs). Async-first: Node, FastAPI, Go, Elixir. Síncronos de raíz: Django, Flask, Rails.

Inyección de dependencias · DI

En vez de que una clase cree por dentro lo que necesita (y quede pegada a ello), alguien de afuera se lo pasa. Sirve para probar (le pasas una base falsa) y para cambiar piezas sin tocar la clase. El framework tiene un "contenedor" que sabe qué entregar a cada quién (NestJS, Spring, Angular).

Los 12 factores · 12-factor app

Un conjunto de reglas para que una app sea fácil de desplegar y escalar en la nube. Las más importantes: la configuración vive en variables de entorno, no en el código; los procesos son sin estado (nada importante en memoria local); las dependencias se declaran explícitamente; dev y producción se parecen lo más posible; los logs se escriben a la salida estándar y otro sistema los recoge. Es la base de casi toda la infraestructura moderna.

Tiempo, zonas horarias y UTC

Guarda todos los instantes en UTC, con un tipo consciente de zona (timestamptz en PostgreSQL, nunca timestamp a secas). Convierte a la zona del usuario solo al mostrar. Un timestamp sin zona es ambiguo: no sabes si esas 15:00 son de Santiago o de Madrid, y cuando lo descubras ya habrá datos históricos sin forma de saberlo.

Trampas El horario de verano hace que una hora local ocurra dos veces o ninguna. "Mañana a esta hora" no es "+24 h" el día del cambio de hora. Para fechas sin hora (cumpleaños, feriados) usa un tipo date, no un instante a medianoche —esa medianoche también tiene zona.

Manejo de dinero · nunca en coma flotante

0.1 + 0.2 no da 0.3 en coma flotante binaria. Con dinero, eso son centavos que aparecen y desaparecen, y cuadraturas que no cierran a fin de mes. Guarda enteros en la unidad mínima (centavos) o un tipo decimal exacto (NUMERIC / DECIMAL en la base, BigDecimal o decimal en el código). Guarda siempre la moneda junto al monto. Redondea solo al final del cálculo y con una regla explícita y escrita.

Por qué importa Es de los bugs más caros y más difíciles de explicarle a un cliente, y se evita por completo eligiendo el tipo correcto el primer día. Cambiarlo después obliga a re-procesar el histórico.

Paginación · offset vs cursor (keyset)

LIMIT 20 OFFSET 10000 obliga a la base a leer y descartar diez mil filas: la página 500 cuesta 500 veces más que la primera. Y si llegan filas nuevas mientras el usuario pagina, verá duplicados o se saltará registros. La paginación por cursor (o keyset) cambia "salta N filas" por "dame lo que viene después de este valor": WHERE (creado, id) < (:ult_creado, :ult_id) ORDER BY creado DESC, id DESC LIMIT 20, apoyada en un índice por esas columnas. Coste constante en cualquier página y estable ante inserciones.

El precio Con cursor no puedes saltar a "página 47" ni mostrar "resultado 900 de 5000". Para APIs, feeds y exportaciones grandes, keyset es el patrón por defecto; OFFSET solo para tablas chicas o pantallas de administración.

Idempotencia de endpoints · claves de idempotencia

Una operación es idempotente si repetirla deja el sistema igual que hacerla una vez. GET, PUT y DELETE lo son por definición; POST no. El problema real: el cliente manda "crear pago", la respuesta se pierde por un corte de red, el cliente reintenta y cobras dos veces. Solución: el cliente genera una clave única por intento lógico y la manda en una cabecera (Idempotency-Key); el servidor guarda esa clave junto con el resultado de la primera vez y, si la clave vuelve, devuelve el mismo resultado sin reejecutar. Es como las APIs de pago serias evitan los cargos dobles.

Por qué importa Todo lo que reintentas —colas, webhooks, el backoff de la sección de sistemas distribuidos— necesita idempotencia del otro lado, o los reintentos corrompen datos en vez de repararlos.

06

Bases de datos a profundidad

La base de datos es casi siempre el cuello de botella y la parte más difícil de cambiar. Vale la pena entenderla de verdad.

El modelo relacional  ·  normalización

Datos en tablas (filas y columnas) conectadas por claves: una clave primaria identifica cada fila, una clave foránea apunta a la primaria de otra tabla. Normalizar es dividir los datos para que cada hecho viva en un solo lugar (no repites el nombre del cliente en cada pedido, lo referencias). Evita inconsistencias. A veces se desnormaliza a propósito —duplicar un dato— para acelerar lecturas.

Índices  ·  el árbol B

Sin índice, buscar una fila obliga a leer toda la tabla (full scan). Un índice es una estructura ordenada aparte —casi siempre un árbol B+— que permite encontrar un valor en pocos saltos, como el índice de un libro. Aceleran las lecturas y frenan las escrituras (hay que mantener el índice), y ocupan espacio. La consulta más común de tu app define qué índices necesitas.

Cómo se depura EXPLAIN delante de una consulta te muestra si usa un índice o hace un full scan. Aprender a leer ese plan es de las habilidades de backend con mejor relación esfuerzo/impacto.

Transacciones  ·  ACID

Una transacción agrupa operaciones que pasan todas o ninguna. ACID: Atomicidad (todo o nada), Consistencia (nunca queda en un estado que viole las reglas), Aislamiento (transacciones simultáneas no se ven a medias), Durabilidad (una vez confirmada, sobrevive a un corte de luz). Es lo que hace que una transferencia bancaria sea confiable.

Niveles de aislamiento

Cuánto se "aíslan" las transacciones concurrentes, de menos a más estricto: read committed (default de PostgreSQL), repeatable read, serializable (como si corrieran una tras otra). Más aislamiento = menos anomalías raras (lecturas fantasma, actualizaciones perdidas) pero más contención. Saber que esto existe evita bugs de concurrencia que solo aparecen bajo carga.

Pool de conexiones · connection pool

Abrir una conexión a la base es caro. Un pool mantiene un puñado de conexiones abiertas y las presta y devuelve. Si tu app pide más de las que hay, el resto espera. Dimensionar mal el pool es una causa clásica de caídas bajo carga.

SQL  vs  NoSQL — las familias

Relacional (PostgreSQL, MySQL): el default; datos estructurados y conectados, transacciones fuertes. Documental (MongoDB): guarda objetos JSON, esquema flexible. Clave-valor (Redis, DynamoDB): un diccionario gigante, rapidísimo, para caché y sesiones. Columnar (ClickHouse, BigQuery): para analítica sobre miles de millones de filas. Grafo (Neo4j): para relaciones densas (redes sociales, fraude). Búsqueda (Elasticsearch): texto libre.

Regla Empieza con PostgreSQL. Hoy cubre documentos (JSONB), clave-valor, búsqueda de texto y hasta vectores para IA. Solo agrega otra base cuando tengas un problema medido que PostgreSQL no resuelve.

Replicación  ·  particionado · sharding

Replicación: copias de la base. Una primaria recibe las escrituras y las propaga a réplicas que sirven lecturas. Escala lecturas y da tolerancia a fallos, pero las réplicas van un instante atrasadas (replication lag). Particionado / sharding: partir los datos en varias bases por algún criterio (por ejemplo, usuarios A-M en una, N-Z en otra). Escala escrituras, a costa de una complejidad enorme: las consultas que cruzan particiones se vuelven difíciles.

La clave primaria · autoincremento vs UUID

Un entero autoincremental (bigserial) es compacto, ordenado y rapidísimo de indexar, pero es adivinable (revela cuántos registros hay), obliga a un ida y vuelta a la base para conocer el id asignado, y complica fusionar datos de varias bases o generar ids sin conexión. Un UUID aleatorio (v4) resuelve eso, pero ocupa 16 bytes y, al ser aleatorio, cada inserción cae en una página distinta del índice → fragmentación y escrituras lentas en tablas grandes.

UUID v7 (estándar RFC 9562, 2024) es el punto medio: lleva un timestamp en los bits altos, así que queda casi ordenado y se indexa casi como un entero, manteniendo la unicidad global. PostgreSQL 18 (2025) trae la función uuidv7() nativa; antes hacía falta una extensión.

Por qué importa Cambiar el tipo de la clave primaria de una tabla grande más adelante es de las migraciones más caras (ver Bases de datos en producción). Decide el primer día pensando en si vas a exponer el id en URLs y en el tamaño que tendrá la tabla en dos años.

Arquitectura de software

Cómo organizas el código y los componentes grandes para que el sistema se pueda entender, cambiar y hacer crecer sin que se convierta en un nudo.

Acoplamiento  ·  cohesión

Acoplamiento: cuánto depende una pieza de otra — bajo es bueno. Cohesión: cuánto tienen que ver entre sí las cosas de una misma pieza — alta es buena. Todo el resto de la arquitectura son técnicas para bajar el acoplamiento y subir la cohesión.

Arquitectura en capas

Dividir por responsabilidad: presentación (rutas de la API, UI) → lógica de negocio (las reglas del dominio) → acceso a datos (hablar con la base). Cada capa solo conoce a la de abajo. Cambiar la base solo toca una capa. Esto es separación de responsabilidades.

Arquitectura hexagonal · puertos y adaptadores

La lógica de negocio ("el núcleo") no sabe nada del mundo exterior. Define puertos (interfaces: "necesito guardar un pedido") y el mundo exterior provee adaptadores que los cumplen (uno para PostgreSQL, uno para pruebas en memoria, uno para una API REST). Puedes probar el núcleo sin base de datos ni red, y cambiar cualquier pieza de infraestructura sin tocarlo.

SOLID

Cinco principios de diseño orientado a objetos. Los dos que más se usan: S — responsabilidad única (una clase, un motivo para cambiar); D — inversión de dependencias (depende de abstracciones, no de implementaciones concretas — la idea detrás de la inyección de dependencias y de la arquitectura hexagonal). Los otros tres (abierto/cerrado, sustitución de Liskov, segregación de interfaces) importan menos a diario.

Patrones de diseño · los que de verdad usarás

Soluciones con nombre a problemas repetidos. Los frecuentes en backend: Repository (aísla el acceso a datos detrás de una interfaz), Factory (centraliza la creación de objetos complejos), Strategy (intercambiar algoritmos: distintos métodos de pago), Adapter (envolver una librería externa con tu propia interfaz), Observer / Pub-Sub (avisar a varios interesados de un evento), Decorator (añadir comportamiento envolviendo). No fuerces patrones: son vocabulario para reconocer estructuras, no una lista de tareas.

Domain-Driven Design · DDD

Modelar el software alrededor del lenguaje del negocio, no de la técnica. Ideas clave: lenguaje ubicuo (código y negocio usan las mismas palabras); contexto acotado (bounded context: "cliente" significa cosas distintas en ventas y en soporte, y está bien que sean modelos separados); agregado (un grupo de objetos que se modifican como una unidad y protegen sus reglas). Vale la pena en dominios complejos; es exceso en un CRUD.

CQRS  ·  event sourcing

CQRS: separar el modelo de escritura del de lectura (por ejemplo, escribes en PostgreSQL normalizado y lees de vistas desnormalizadas o de Elasticsearch). Event sourcing: en vez de guardar el estado actual, guardas la lista completa de eventos que ocurrieron ("creado", "pagado", "enviado") y reconstruyes el estado sumándolos. Potente para auditoría, pero mucha complejidad — reservado a casos que lo justifican.

Monolito  ·  microservicios  ·  serverless

Monolito: un solo programa. Simple de desarrollar, probar y desplegar. Microservicios: muchos programas chicos, uno por área, que se hablan por la red. Cada equipo despliega el suyo y se escala solo lo necesario — a cambio de una complejidad operativa enorme (fallos parciales, latencia de red, monitoreo distribuido, consistencia entre servicios). Serverless: funciones que el proveedor ejecuta bajo demanda y apaga; pagas por uso, sufren arranque en frío.

Regla Casi siempre se empieza con un monolito bien modularizado. Los microservicios resuelven problemas de escala organizativa (muchos equipos pisándose) que la mayoría no tiene. "Monolito primero" es el consejo por defecto de casi toda la industria.

El patrón outbox · el problema de la doble escritura

Quieres guardar un pedido en la base y publicar un evento "pedido creado" en una cola. Si haces las dos cosas por separado, una puede fallar: pedido guardado y evento perdido, o evento emitido y transacción revertida. No existe una transacción que abarque la base y la cola a la vez.

Outbox: en la misma transacción que escribe el pedido, insertas una fila en una tabla outbox. Un proceso aparte lee esa tabla, publica en la cola y marca cada fila como enviada. Así el evento existe si y solo si el pedido se guardó. La entrega es "al menos una vez", de modo que los consumidores deben ser idempotentes.

Por qué importa Es la forma estándar de conectar una base de datos con un bus de eventos sin perder ni duplicar mensajes de forma silenciosa. Herramientas de change data capture como Debezium implementan la misma idea leyendo el registro de cambios de la base en lugar de una tabla.

Sistemas distribuidos y escala

En cuanto hay más de una máquina, aparecen problemas nuevos: la red falla, los relojes no coinciden, y "el estado del sistema" deja de ser una sola verdad.

Las 8 falacias de la computación distribuida

Suposiciones falsas que todos hacemos al principio: la red es confiable, la latencia es cero, el ancho de banda es infinito, la red es segura, la topología no cambia, hay un solo administrador, el coste de transporte es cero, la red es homogénea. Cada bug serio de un sistema distribuido es una de estas mordiendo.

Teorema CAP

Cuando hay una partición de red (dos mitades del sistema no se pueden hablar), tienes que elegir: Consistencia (todos ven el mismo dato, aunque haya que rechazar peticiones) o Availability (todos reciben respuesta, aunque sea de un dato viejo). No puedes tener ambas durante la partición. En la práctica se extiende con PACELC: y cuando NO hay partición, eliges entre latencia y consistencia.

Consistencia fuerte  vs  eventual

Fuerte: después de escribir, cualquier lectura ve el valor nuevo. Eventual: las lecturas pueden ver el valor viejo un rato, pero "con el tiempo" convergen. Muchísimos sistemas a escala (carritos, contadores de "me gusta", feeds) eligen eventual a propósito porque es mucho más barata y el usuario no nota el retraso.

Cachés y su invalidación

Guardar un resultado caro para no recalcularlo. Estrategias: cache-aside (la app consulta la caché; si no está, va a la base y la llena), write-through (escribe en caché y base a la vez). El problema difícil es la invalidación: cuándo borrar el dato viejo. Herramientas: expiración por tiempo (TTL), borrado explícito al cambiar el dato. "Solo hay dos problemas difíciles en informática: invalidar cachés y nombrar cosas."

Colas de mensajes  ·  arquitectura orientada a eventos

Una tarea lenta (enviar 10.000 emails, procesar un video) no se hace durante la petición: se pone un mensaje en una cola y un proceso aparte (worker) lo consume. Pub-Sub: un evento ("pedido pagado") se publica y varios servicios reaccionan (facturación, envío, analítica) sin que el emisor sepa de ellos. Desacopla y absorbe picos. Herramientas: RabbitMQ, Kafka, Redis, SQS, NATS.

Backpressure  ·  rate limiting

Backpressure: cuando un componente recibe más de lo que puede procesar, necesita una forma de decir "más lento" en vez de reventar. Rate limiting: límite de peticiones por cliente y ventana de tiempo, para protegerte de abuso y de picos. Algoritmos: token bucket (el más usado), ventana deslizante.

Reintentos, backoff y jitter

Si una llamada falla por algo transitorio, reintentas — pero no de inmediato ni siempre igual: backoff exponencial (espera 1s, 2s, 4s, 8s...) para no martillar un servicio caído, más jitter (un poco de azar) para que mil clientes no reintenten todos en el mismo milisegundo (el "rebaño atronador"). Y solo reintenta operaciones idempotentes.

Circuit breaker · cortacircuitos

Si un servicio del que dependes está caído, seguir llamándolo desperdicia recursos y propaga la caída. El cortacircuitos detecta la racha de fallos, "abre el circuito" y durante un tiempo falla rápido sin ni siquiera intentar la llamada, dando tiempo al otro servicio a recuperarse. Patrón de Release It!.

Balanceo de carga  ·  CDN

Un balanceador reparte peticiones entre varios servidores idénticos (algoritmos: round-robin, least connections, por hash de IP). Requiere que los servidores sean sin estado. Una CDN (Cloudflare, CloudFront) es una red de servidores caché repartidos por el mundo que sirven contenido estático (imágenes, JS, CSS) desde el punto más cercano al usuario.

Presupuesto de latencia y deadlines

Si tu endpoint promete responder en 300 ms y por dentro llama a tres servicios en serie, no puedes darle 250 ms de timeout a cada uno: el presupuesto total son 300 ms y hay que repartirlo. Cada llamada hacia abajo recibe un deadline igual a lo que queda del presupuesto, no un timeout fijo, y ese deadline se propaga en la petición (una cabecera, el contexto de gRPC) para que un servicio no siga trabajando en algo cuyo cliente ya se rindió.

Sin esto, un servicio lento aguas abajo hace que se acumulen peticiones aguas arriba —cada una esperando su timeout largo—, se agotan los hilos y las conexiones, y la caída se propaga hacia el usuario. Timeout agresivo + reintento idempotente + circuit breaker es el trío que lo contiene.

Cache stampede · estampida de caché

Una clave de caché muy consultada expira. En ese instante, mil peticiones fallan la caché a la vez y todas van a recalcular lo mismo contra la base, que se cae por la avalancha (también: dogpile, thundering herd). Defensas: recomputación anticipada —renovar la clave un poco antes de que expire, de forma probabilística; un lock o lease para que solo una petición recalcule y el resto espere o sirva el valor viejo; TTL con jitter para que las claves no expiren todas juntas; y no cachear con expiración dura lo que puedas invalidar de forma explícita al cambiar el dato.

Por qué importa La caché que "funciona en las pruebas" falla justo cuando hay más tráfico, que es cuando esa clave está más caliente y su expiración hace más daño.

Seguridad

No es una fase al final: es una forma de escribir cada línea que toca datos que vienen de fuera. La regla base: nunca confíes en la entrada del cliente.

Inyección · SQL, comandos, etc.

Si construyes una consulta pegando texto del usuario ("SELECT ... WHERE nombre = '" + entrada + "'"), el usuario puede cerrar la comilla y escribir su propio SQL. La defensa es consultas parametrizadas: el driver recibe la consulta y los datos por separado y nunca mezcla. Todo ORM decente lo hace por defecto. Lo mismo aplica a construir comandos del sistema con entrada del usuario.

XSS · cross-site scripting

Si muestras texto del usuario en una página sin escaparlo, alguien puede meter <script> que se ejecuta en el navegador de otras víctimas (robar su sesión, por ejemplo). Defensa: escapar toda salida (los motores de plantillas modernos lo hacen solos) y una cabecera Content-Security-Policy.

CSRF  ·  CORS

CSRF: otra web hace que tu navegador envíe una petición a un sitio donde estás logueado, usando tu cookie sin tu permiso. Defensa: tokens CSRF o cookies SameSite. CORS es lo contrario y se confunde siempre: es la regla del navegador que bloquea que una web llame a una API de otro dominio salvo que la API lo permita explícitamente con cabeceras. CORS no es una protección tuya, es una del navegador.

Control de acceso roto

El fallo más común según OWASP: el endpoint verifica que estás autenticado pero no que ese recurso es tuyo. GET /facturas/1005 te devuelve la factura de otro con solo cambiar el número (IDOR). Cada consulta debe filtrar por el usuario del token, siempre.

OWASP Top 10

La lista de referencia de los riesgos más frecuentes en aplicaciones web, actualizada cada pocos años por la OWASP Foundation. Incluye control de acceso roto, fallos criptográficos, inyección, diseño inseguro, mala configuración, componentes vulnerables, fallos de autenticación, fallos de integridad, fallos de registro y monitoreo, y SSRF. Gratis, con guías de mitigación. Léela entera una vez.

TLS / HTTPS  ·  secretos  ·  mínimo privilegio

TLS cifra el canal entre cliente y servidor y verifica la identidad del servidor con un certificado (gratis y automático con Let's Encrypt). Secretos (claves de API, contraseñas de la base) nunca en el repo: en variables de entorno o en un gestor (Vault, AWS Secrets Manager). Mínimo privilegio: cada componente tiene solo los permisos que necesita — el usuario de base de datos de tu app no debería poder borrar tablas.

El ciclo de vida y el testing

Cómo nace un software y llega a manos de usuarios. Siete fases; cada vuelta al ciclo es más chica y rápida que la anterior.

Fase 0 Idea y descubrimiento

Problema antes que solución. Requisitos funcionales (qué hace) vs no funcionales (cuán rápido, cuánta carga, qué disponibilidad — estos definen la arquitectura). MVP = la versión mínima que ya sirve. Historias de usuario: "Como rol, quiero acción, para beneficio".

Fase 1 Diseño y arquitectura

Cajas y flechas, elección de stack, arquitectura en capas, modelo de datos, contrato de la API antes de implementar, y un ADR (documento corto con el porqué) por cada decisión difícil de revertir.

Fase 2 Preparar el terreno

Repo Git, gestión de dependencias, secretos en variables de entorno, y los entornos: desarrollo (tu máquina), staging (copia de prueba), producción.

Fase 3 Construcción

Rama → commits pequeños → Pull Request → code review → CI en verde → merge. Un linter marca errores mientras escribes; un formatter unifica el estilo.

Fase 4 Calidad — el testing en detalle

TDD (test-driven development): escribes el test primero, lo ves fallar, escribes el código mínimo para pasarlo, refactorizas. Dobles de prueba: un stub devuelve respuestas fijas, un mock además verifica que se le llamó como esperabas, un fake es una implementación simplificada de verdad (una base en memoria). Fase 5 Despliegue

El build produce un artefacto (binario, o los archivos del frontend minimizados). Un contenedor lo empaqueta con todo lo que necesita. CI/CD: si los tests pasan, se despliega. Estrategias: rolling (servidores de a poco), blue-green (versión nueva completa al lado, se cambia de golpe), canary (5% del tráfico primero). Feature flags: interruptores que activan o desactivan una función sin desplegar, para lanzar a un % de usuarios o apagar algo roto al instante. Infraestructura como código (Terraform): describes los servidores en archivos y una herramienta los crea.

Fase 6 Operación

Observabilidad (sección siguiente), alertas, escalado, backups probados, y postmortems sin culpar a personas tras cada incidente.

Fase 7 Evolución

El feedback genera nuevas ideas → Fase 0. La deuda técnica son los atajos que ahora frenan; se paga refactorizando. Versionado semántico MAYOR.MENOR.PARCHE.

Trunk-based vs GitFlow

Dos formas de organizar las ramas. GitFlow: ramas de larga vida (develop, release, hotfix) — pesado, para releases con calendario. Trunk-based: ramas cortísimas que se fusionan a main varias veces al día, protegidas por feature flags y CI fuerte. La industria moderna favorece trunk-based; es lo que mide Accelerate como práctica de los equipos de alto rendimiento.

Observabilidad y confiabilidad

Publicar no es el final. Un sistema en producción hay que poder verlo y tener un acuerdo explícito de cuán confiable debe ser.

Los tres pilares

Logs: eventos línea por línea — "¿qué pasó a las 14:32?". Deben ser estructurados (JSON con campos, no texto libre) para poder filtrarlos. Métricas: números en el tiempo (peticiones/seg, latencia, CPU, errores) — "¿está sano ahora?". Trazas: el recorrido completo de una petición por todos los servicios — "¿en qué salto se demoró?".

Percentiles, no promedios

La latencia promedio miente: si 99 peticiones tardan 10 ms y una tarda 5 s, el promedio es 60 ms y nadie está feliz. Se mira p50 (la mediana), p95 y p99 (el 1% peor). El p99 es lo que sienten tus usuarios más activos.

Métodos RED y USE

Qué medir, resumido. RED para servicios: Rate (peticiones/seg), Errors (cuántas fallan), Duration (latencia). USE para recursos (CPU, disco, red): Utilization, Saturation, Errors.

SLI · SLO · SLA · error budget

SLI (indicador): una métrica concreta, "% de peticiones que responden bien en menos de 300 ms". SLO (objetivo): la meta interna, "99,9% al mes". SLA (acuerdo): la promesa contractual al cliente, con penalización si no se cumple — siempre más laxa que el SLO. Error budget: si tu SLO es 99,9%, tienes un 0,1% de "presupuesto" de fallos al mes; mientras no lo agotes, puedes arriesgar lanzando features; si lo agotas, congelas y estabilizas. Idea central de SRE.

Monitoreo de errores  ·  on-call

Una herramienta (Sentry) captura cada excepción en producción, la agrupa y dice a cuántos usuarios afectó y en qué línea. Alertas conectadas a un turno on-call: alguien responde si algo se rompe. Regla: alerta solo sobre síntomas que afectan al usuario, no sobre cada métrica rara — las alertas ruidosas se ignoran.

IDs de correlación · trace context

Una petición del usuario toca el balanceador, dos servicios y la base. Si cada componente escribe sus logs por su lado, reconstruir "qué pasó con la petición de Ana a las 14:32" es casi imposible. Al entrar la petición se genera un identificador único (o se acepta el que ya trae) y se propaga por todos los saltos en una cabecera estándar (traceparent, de W3C Trace Context, o X-Request-Id). Todos los logs de esa petición llevan ese campo, así que un solo filtro te da la historia completa.

Por qué importa Es el pegamento entre los tres pilares: desde una traza saltas a sus logs, desde un error saltas a su traza. Sin esto, la observabilidad en un sistema con más de un servicio no sirve para depurar incidentes reales, solo para hacer gráficos bonitos.

Sostenibilidad: mucha infraestructura crítica la mantiene gente gratis, a veces una sola persona quemada. Git, GitHub y de dónde sacar proyectos

Git guarda el historial en tu máquina. GitHub o GitLab alojan una copia en la nube más las herramientas de colaboración y automatización.

Bases de datos en producción

Entre "sé escribir consultas" y "opero una base con datos de gente real" hay un salto que casi ningún curso cubre: backups que de verdad restauran, recuperar a un instante exacto, réplicas, failover sin perder datos, y cambiar el esquema de una tabla de millones de filas sin cortar el servicio. Es la zona que separa a un backend que funciona en tu máquina de uno que aguanta un lunes por la mañana.

Backups · lógico vs físico, completo vs incremental

Un dump lógico (pg_dump, mysqldump) exporta el contenido como sentencias SQL o un formato propio: es portable entre versiones y arquitecturas, permite restaurar una sola tabla, pero es lento y en bases grandes tarda horas. Un backup físico copia los archivos de datos tal cual —a nivel de bloque— con pg_basebackup, un snapshot del volumen, o herramientas como pgBackRest, Barman o WAL‑G: es rápido, restaura la instancia entera y es la base sobre la que se construye el PITR, a cambio de quedar atado a la versión y la plataforma.

Un backup completo copia todo; uno incremental o diferencial solo lo que cambió desde el anterior (bloques modificados, o el registro de cambios). Ocupa menos y acorta la ventana de copia, a costa de una restauración que encadena varios archivos. Y la regla 3‑2‑1: tres copias, en dos medios, una fuera del sitio. Un backup en el mismo disco, región o cuenta que la base no es un backup: un borrado accidental o un compromiso de la cuenta se lo lleva con todo.

Cómo se verifica Un backup no probado no existe. El pg_dump que falla a la mitad y nadie mira el código de salida; el snapshot de un volumen tomado con la base escribiendo, que produce una imagen incoherente. La única prueba es el restore drill: restaurar el backup en una máquina limpia, arrancar la base, correr comprobaciones de integridad y cronometrar. Trimestral como mínimo. El número que sale de ahí es tu tiempo de recuperación real, no el del papel.

RPO  ·  RTO

RPO (recovery point objective): cuántos datos te puedes permitir perder, medido en tiempo. Si el único backup es de cada noche, tu RPO es de hasta 24 horas de trabajo. Con archivado continuo del registro de cambios baja a segundos. RTO (recovery time objective): cuánto puede estar caído el servicio mientras recuperas. Depende del tamaño de la base, del tipo de backup, del ancho de banda de restauración y —sobre todo— de si el procedimiento está automatizado y practicado o se improvisa a las 3 de la mañana.

De dónde salen Los dos números los pone el negocio, no la infraestructura: "perder una hora de pedidos" cuesta una cifra concreta, y a partir de ella se decide cuánto invertir. Prometer RPO 0 y RTO de minutos es caro (réplicas síncronas, failover automático, drills frecuentes); para un proyecto interno puede bastar "perdemos como mucho un día y volvemos en cuatro horas". Lo que no vale es no haberlo decidido.

PITR · recuperación a un punto en el tiempo

La idea: un backup base físico tomado en un instante T0, más el flujo continuo de todos los cambios posteriores —el WAL (write-ahead log) en PostgreSQL, el binlog en MySQL— archivado a un almacenamiento aparte. Para recuperar el estado que había a las 14:32:07 tomas el backup base más reciente anterior a esa hora y reproduces el registro de cambios hasta el instante exacto (recovery_target_time).

Para qué sirve de verdad: alguien corrió DELETE FROM facturas sin WHERE a las 14:30. Con PITR restauras a las 14:29:59 y pierdes un minuto. Sin PITR solo tienes el backup de anoche y pierdes el día entero. Necesitas las dos piezas: el backup base solo te lleva a T0; el WAL por sí solo no sirve sin una base desde donde aplicarlo. Por eso se archivan juntos y se prueban juntos.

La trampa silenciosa El archivado tiene que estar sano. Si el comando que copia el WAL al almacén falla sin que nadie lo note, pasan dos cosas malas: PostgreSQL acumula WAL en el disco de la primaria hasta llenarlo (y entonces la base se detiene), y tu ventana de PITR deja de avanzar —crees que puedes recuperar a "hace 5 minutos" y en realidad solo llegas a anteayer. Monitorear el retraso de archivado es obligatorio, no opcional. El WAL es también lo que da la D de ACID y lo que alimenta la replicación.

Réplicas · streaming replication

La primaria envía su flujo de WAL a una o más réplicas que lo aplican y quedan como copia casi en vivo. Sirve para cuatro cosas: escalar lecturas (read replicas), tolerancia a fallos (una réplica es candidata a primaria), tomar backups sin cargar a la primaria, y poner datos geográficamente cerca de los usuarios.

Replicación física: copia bloque a bloque, toda la instancia idéntica (el streaming nativo de PostgreSQL, MySQL con GTID). Replicación lógica: decodifica el WAL a cambios de fila y los reproduce; permite replicar entre versiones distintas, solo un subconjunto de tablas, o hacia otro sistema —es la base del change data capture hacia un almacén analítico.

Asíncrona (lo normal): la primaria confirma el commit al cliente sin esperar a las réplicas. Rápida, pero si la primaria muere antes de propagar, esas últimas transacciones se pierden —el RPO deja de ser cero. Síncrona: la primaria espera el acuse de al menos una réplica antes de confirmar; RPO cero para lo confirmado, a costa de sumar la latencia de red a cada escritura y del riesgo de que, si la réplica síncrona se cae, las escrituras se bloqueen (por eso se tienen dos o más candidatas). Quórum: "espera el acuse de cualquier 2 de estas 3" —el mismo principio de mayoría que en sistemas distribuidos, equilibrando durabilidad y disponibilidad.

Replication lag · y la trampa de leer de una réplica

El lag es cuánto va por detrás una réplica respecto a la primaria, en tiempo o en bytes de WAL pendientes. Causas típicas: un pico de escrituras que la réplica aplica con menos paralelismo del que la primaria usó para generarlas; una consulta larga en la réplica que entra en conflicto con la aplicación del WAL; red saturada; disco de la réplica más lento. Se mide desde la primaria con pg_stat_replication o en la réplica con pg_last_xact_replay_timestamp(), y se expone como métrica con alerta.

El bug que genera Mandas la lectura a una read replica justo después de una escritura y no ves tu propio cambio: "creé el usuario y el panel dice que no existe". Es consistencia eventual mordiendo. Patrones para evitarlo: leer de la primaria durante unos segundos tras escribir (read-your-writes), fijar la sesión del usuario a la primaria un rato, o esperar a que la réplica alcance el punto del WAL de tu commit antes de leer de ella. Regla simple: a una réplica solo mandas lecturas que toleran datos de hace un instante (informes, listados, búsquedas), nunca la lectura que confirma una escritura que acabas de hacer.

Failover y promoción · split-brain, fencing

Failover es promover una réplica a primaria cuando la primaria cae. Manual: un humano confirma que está muerta y ejecuta la promoción —seguro pero lento, minutos. Automático: un supervisor lo detecta y promueve en segundos, a cambio del riesgo de promover por un falso positivo (la primaria no estaba muerta, solo aislada de la red un momento).

El split-brain es el peor fallo posible de una base: dos nodos se creen primaria a la vez y ambos aceptan escrituras, y los datos divergen de forma irreparable. Se evita con tres capas: un consenso sobre un almacén externo (etcd, Consul, ZooKeeper) que actúa de árbitro y solo deja una primaria; un quórum de nodos, para que un nodo aislado en minoría nunca se autopromueva; y fencing / STONITH (shoot the other node in the head): aislar de verdad a la vieja primaria —matar su proceso, quitarle la IP virtual, un watchdog por hardware— antes de promover a la sustituta.

Qué pasa con las conexiones y las herramientas En un failover, todas las conexiones a la vieja primaria se cortan y las transacciones en vuelo se pierden: la aplicación ve errores hasta que el pool reconecta, y tiene que reintentar las operaciones (idempotentes, si no las duplicará). Un proxy que abstrae el endpoint (RDS Proxy, HAProxy con health checks, el DNS que Patroni reapunta) acorta el corte. Herramientas: Patroni (PostgreSQL + etcd, el estándar de facto), pg_auto_failover (nodo monitor + testigo), orchestrator (MySQL, creado en GitHub), y los servicios gestionados —RDS Multi‑AZ, Aurora, Cloud SQL— que hacen el failover en decenas de segundos sin que administres el consenso.

Locks: el peligro real de una migración

En PostgreSQL, muchas sentencias ALTER TABLE toman un lock ACCESS EXCLUSIVE sobre la tabla. El detalle que tumba producción: ese ALTER se pone en cola detrás de cualquier transacción abierta sobre la tabla —incluida una consulta de informe de diez minutos o un autovacuum— y, mientras espera, todas las consultas nuevas, incluidos los SELECT, se encolan detrás de él. Una migración "instantánea" con una transacción lenta por delante congela la tabla entera durante minutos.

Defensa: SET lock_timeout = '2s' antes de cada sentencia DDL para que falle rápido en vez de bloquear en cadena; aplica los cambios en pasos pequeños; crea índices siempre con CREATE INDEX CONCURRENTLY; y nunca corras una migración a la vez que un proceso por lotes o una ventana de mucho tráfico.

Connection pooling · por qué y con qué

PostgreSQL asigna un proceso del sistema operativo por conexión, no un hilo. Cada conexión consume memoria y el planificador de la CPU se resiente con miles. Pasado un punto —del orden de unos cientos de conexiones activas— el rendimiento total baja aunque la CPU no esté saturada. MySQL usa hilos y aguanta más, pero también tiene techo. Por eso se pone un pooler externo que mantiene unas pocas conexiones reales a la base y multiplexa sobre ellas muchas conexiones de aplicación.

PgBouncer, sus modos: session —una conexión de servidor por cliente mientras dura su sesión; casi no multiplexa, solo limita el total. transaction —la conexión de servidor se presta solo durante una transacción y vuelve al pool en el COMMIT; es el modo útil (diez mil clientes sobre veinte conexiones reales), pero rompe lo que depende de estado de sesión: SET, advisory locks, LISTEN/NOTIFY, cursores WITH HOLD, y los prepared statements —soportados desde PgBouncer 1.21 activando max_prepared_statements. statement —devuelve la conexión tras cada sentencia; prohíbe transacciones de varias sentencias; nicho.

Tamaño del pool y serverless El pool no se hace grande "por si acaso": un pool enorme traslada la contención a la base. Un punto de partida razonable es del orden de unas decenas de conexiones —cercano al número de núcleos de la base—, con la regla de que si las peticiones hacen cola, mejor que la cola esté en el pooler (visible y barata) que en la base. En serverless (Lambda, funciones en el borde) cada instancia quiere su conexión y escalan a cientos en un pico: un pooler en modo transaction delante (RDS Proxy, PgBouncer, Supavisor, o el endpoint agrupado del proveedor) deja de ser opcional. Ver también el pool de conexiones y las capas de los datos.

Migraciones sin downtime · expand / contract

También llamado parallel change. La regla: nunca cambias el esquema y el código a la vez; divides el cambio en fases donde en todo momento el esquema es compatible con la versión de código anterior y con la siguiente.

Expand — añades lo nuevo sin tocar lo viejo: una columna nullable, una tabla, un índice. El código en producción los ignora. Migrate / backfill — despliegas el código nuevo, que empieza a escribir en los dos sitios (o un trigger lo hace), y un proceso rellena las filas históricas por lotes —mil a diez mil filas, commit, pausa, repetir— nunca un UPDATE único de cincuenta millones de filas que toma un lock larguísimo y genera un WAL gigante. Contract — cuando el código nuevo está desplegado en todas partes y el backfill terminó, quitas lo viejo: la columna, el trigger, el código de doble escritura.

Casos concretos: una columna NOT NULL nueva no se añade directa (valida toda la tabla bajo lock) sino nullable → backfill → restricción CHECK ... NOT VALID → VALIDATE CONSTRAINT (lock suave). Un índice siempre con CREATE INDEX CONCURRENTLY (no bloquea escrituras, tarda más, y si falla deja un índice inválido que hay que borrar). Renombrar una columna es expand/contract puro —un RENAME directo rompe el código viejo al instante. Cambiar el tipo de una clave que se está agotando (int → bigint): columna nueva, doble escritura, backfill por lotes, intercambio. Herramientas que automatizan esto: pgroll (PostgreSQL, sirve varias versiones del esquema como vistas), gh-ost y pt-online-schema-change (MySQL, tabla sombra con triggers).

Feature flags para el esquema El paso de "leer de la columna vieja" a "leer de la nueva" se controla con un feature flag, no con un despliegue: si algo va mal, lo apagas en segundos sin revertir la migración. Y siempre lock_timeout + statement_timeout en la sesión que corre la migración. Enlaza con migraciones como concepto base.

Particionado en caliente · por rango, lista, hash

Partir una tabla lógica en varias tablas físicas por una clave. Por rango (una partición por mes, lo más común, para datos con ciclo de vida). Por lista (por país, por tenant). Por hash (repartir de forma uniforme cuando no hay una clave de rango natural).

Cuándo: cuando la tabla es tan grande que el mantenimiento duele —el VACUUM tarda horas, los índices no caben en memoria, borrar datos viejos con DELETE genera bloat. Con particiones, "borrar el mes pasado" es un DETACH o DROP instantáneo. Regla de dedo: por encima de decenas de millones de filas, o siempre que haya una política de retención por fecha.

Pruning y el error clásico El partition pruning hace que el planificador salte las particiones que la consulta no necesita —pero solo si la clave de partición está en el WHERE. Particionar por fecha y luego filtrar solo por user_id recorre todas las particiones igual. Particionar una tabla que ya es grande sin cortar el servicio es un proyecto —tabla particionada nueva al lado, copia por lotes, doble escritura, intercambio de nombres— no un ALTER. La extensión pg_partman crea y rota particiones sola. Y particionado no es sharding: las particiones viven en la misma instancia.

Escalar la base · el orden correcto

1 · Vertical — una máquina más grande. Siempre lo primero: barato en esfuerzo y llega lejos (hoy hay instancias de cientos de núcleos y terabytes de RAM). Techo: existe una máquina máxima, y la escritura sigue en un solo nodo. 2 · Read replicas — si el grueso del tráfico son lecturas, repártelas. Barato; no ayuda a las escrituras y trae el problema del lag. 3 · Caché (Redis) delante para las lecturas calientes —a menudo evita los dos pasos siguientes durante años. 4 · Sharding — repartir los datos entre instancias por una clave (tenant, usuario). Escala escrituras de verdad, a cambio de consultas cross-shard difíciles, transacciones distribuidas, rebalanceo, y una clave que si eliges mal duele años. Último recurso. 5 · Motores que shardean por ti — Citus (extensión de PostgreSQL que distribuye tablas entre nodos worker) o Vitess (MySQL, el que mueve YouTube): te quitan parte del dolor operativo, no la complejidad conceptual.

Connection storm Cuando la base se reinicia o hace failover, todas las aplicaciones reconectan a la vez y la avalancha de handshakes la vuelve a tumbar —el "rebaño atronador" aplicado a conexiones. Se mitiga con backoff y jitter en el driver, un límite de conexiones nuevas por segundo en el pooler, y arranque escalonado de los servicios de aplicación.

Checklist · ¿esta base está lista para producción?

Antes de que reciba datos de gente real, deberías poder marcar todo esto:

▸ Backups automáticos y una restauración probada de verdad este trimestre, con el tiempo de recuperación cronometrado.   ▸ Archivado de WAL / binlog sano y monitoreado —PITR real, no solo el dump nocturno.   ▸ RPO y RTO escritos y acordados con el negocio.   ▸ Al menos una réplica en otra zona, y un failover probado (aunque sea manual y documentado en un runbook).   ▸ Un pooler de conexiones delante, con el pool dimensionado y métricas de espera.   ▸ Procedimiento de migraciones escrito: lock_timeout, índices CONCURRENTLY, expand/contract.   ▸ Métricas con alerta: conexiones, lag de réplica, lag de archivado, ratio de acierto de caché, consultas lentas (pg_stat_statements), edad de la transacción más antigua, y espacio en disco (alerta al 70%).   ▸ Un statement_timeout global para que una consulta desbocada no se lleve todo por delante.   ▸ Credenciales rotables; el usuario de la aplicación no es superusuario.

Tres proyectos de punta a punta

El mismo ciclo de siete fases, tres lenguajes, tres tipos de framework. Fíjate en cuánto cambia la experiencia según cuánto te da el framework.

Go + Chi + PostgreSQL · framework micro

Acortador de URLs con analíticas

Recibe una URL larga, devuelve un código corto. Al visitar el código, redirige. Cuenta visitas.

Fase 0IdeaFuncional: crear enlace, redirigir, ver conteo. No funcional: la redirección se usa muchísimo → rápida; el código único e impredecible.
Fase 1ArquitecturaMonolito. Tabla links(id, codigo, url_larga, visitas, creado). API: POST /links, GET /{codigo} (301). ADR: código de 7 caracteres aleatorios base62, no secuencial. Caché en memoria para los más visitados.
Fase 2TerrenoRepo Git, go mod init, PostgreSQL local con Docker, variable DATABASE_URL.
Fase 3ConstrucciónRama, handler con Chi, consultas con database/sql, migración 001_crear_links.sql. PR + review.
Fase 4CalidadUnitario del generador de códigos (largo, sin repetir). Integración del endpoint contra un PostgreSQL de prueba. CI: go test ./....
Fase 5Desplieguego build → binario único. Dockerfile de dos líneas. Deploy a un VPS o Fly.io. Dominio + HTTPS automático.
Fase 6OperaciónLog de cada redirección. Métrica de latencia p95. Alerta si los 5xx superan el 1%. Backup diario.
Fase 7EvoluciónEnlaces con expiración, códigos personalizados → Fase 0.

Qué aprendesHTTP sin magia, diseño de esquema, migraciones, caché, diseño sin estado, binario + Docker. El ciclo entero con mínima fricción.

Python + FastAPI + PostgreSQL · micro, API-first

API de gastos personales

Registrar gastos, categorizarlos, ver totales por mes. Con usuarios: cada quien ve solo lo suyo. La consume una app móvil.

Fase 0IdeaHistorias: "registrar un gasto con monto, categoría y fecha", "ver mi total del mes". No funcional: datos privados por usuario; cliente móvil → contrato claro y documentado.
Fase 1ArquitecturaMonolito API-first. Tablas usuarios, gastos. Auth JWT. Endpoints REST + /gastos/resumen?mes=. Validación Pydantic. ADR: JWT stateless sobre sesiones, para no depender de cookies.
Fase 2TerrenoRepo, venv, requirements.txt, PostgreSQL en Docker, .env con SECRET_KEY, Alembic para migraciones.
Fase 3ConstrucciónModelos SQLAlchemy, esquemas Pydantic. Dependencia get_current_user que valida el token (inyección de dependencias). Cada consulta filtra por el usuario_id del token.
Fase 4CalidadUnitarios del resumen. Integración con TestClient. Test de seguridad: el usuario A no puede leer los gastos de B (404). CI: pytest + ruff.
Fase 5DespliegueDocker. Deploy a Render/Fly/Railway o VPS con Uvicorn + Nginx. alembic upgrade head al arrancar. HTTPS.
Fase 6OperaciónSentry. Logs JSON. Métrica de latencia. Las docs OpenAPI en /docs las usa el equipo móvil.
Fase 7EvoluciónExportar a CSV, presupuestos por categoría con alertas → Fase 0.

Qué aprendesREST de verdad, autenticación y autorización, JWT, validación con esquemas, migraciones con Alembic, async, tests de seguridad, el "contrato" de una API.

PHP + Laravel + MySQL · full-stack (MVC)

Blog con panel de administración

Un blog público más un panel privado donde el autor —que no es técnico— crea, edita y borra posts y sube imágenes.

Fase 0IdeaHistorias: "leer artículos", "publicar sin tocar código". No funcional: SEO (URLs limpias /blog/mi-titulo); el autor no programa.
Fase 1ArquitecturaFull-stack MVC, monolito. Laravel renderiza HTML en el servidor (Blade). Tablas users, posts. Rutas públicas y /admin protegidas. ORM Eloquent. Auth de sesión (cookies) — aquí sí conviene sesión, es web con navegador.
Fase 2TerrenoRepo, Composer, .env con MySQL, Laravel Sail (Docker), php artisan migrate.
Fase 3ConstrucciónMigraciones con artisan make:migration. Modelos Eloquent con User hasMany Post. Controladores, vistas Blade, middleware auth en /admin. El slug se genera del título solo.
Fase 4CalidadTests de feature (Pest): "un visitante ve los posts publicados", "un no autenticado no entra a /admin". CI: php artisan test + Pint.
Fase 5DespliegueVPS con PHP-FPM + Nginx, o Laravel Forge. php artisan migrate --force en el deploy. Assets con Vite. HTTPS.
Fase 6OperaciónLogs de Laravel. Sentry. Monitoreo de uptime. Backup diario de MySQL.
Fase 7EvoluciónComentarios, categorías, borradores programados → Fase 0.

Qué aprendesEl modelo MVC, ORM y relaciones, plantillas del lado servidor, sesiones vs tokens, el flujo "con pilas incluidas" donde el framework ya resolvió auth, migraciones y panel.

La comparación

Las siete fases son siempre las mismas. Lo que cambia es cuánto te da el framework: en Go escribes el router y casi todo; en FastAPI tienes validación y docs gratis pero pones ORM y login; en Laravel el ORM, las migraciones, el login y el panel ya vienen. Menos código no es siempre mejor — es menos control y más "magia" que entender cuando algo falla.

Reglas para que funcione

  1. Un proyecto terminado —desplegado, con README, con tests— enseña más que diez tutoriales a medias. La columna "entregable" es la que importa.
