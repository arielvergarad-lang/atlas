01

Cómo el navegador pinta una página

Entre el HTML que llega por la red y los píxeles en pantalla hay una tubería fija de etapas. Saber en qué etapa cae cada cambio explica por qué animar transform va fluido y animar width traba el scroll.

Parseo: bytes → tokens → nodos → DOM · construcción del árbol

El navegador recibe bytes, los decodifica según la codificación declarada, el tokenizador reconoce etiquetas y atributos, y el constructor de árbol arma el DOM: una estructura en memoria, no el texto. El parser de HTML es tolerante: cierra etiquetas que faltan y sigue.

por qué importaUn <script> sin async ni defer detiene el parser hasta descargar y ejecutar ese script: el DOM deja de crecer mientras tanto.

CSS → CSSOM · bloqueante para pintar

El CSS se parsea a otro árbol, el CSSOM, con la cascada ya resuelta. El navegador no pinta nada hasta tener todo el CSS que podría aplicar, porque una regla al final de la hoja puede cambiarlo todo. Sin esta espera verías un destello de página sin estilo en cada carga.

por qué importaEl CSS crítico va en línea o en un archivo pequeño y temprano; el resto se difiere. Una hoja de estilos gigante retrasa el primer pixel de toda la página.

Render tree · solo lo visible

DOM y CSSOM se combinan en el árbol de render, que contiene únicamente los nodos que se van a dibujar con su estilo calculado. display:none deja el nodo fuera del árbol; visibility:hidden lo mantiene (ocupa espacio, no se ve).

Layout (reflow) · geometría

Calcula la posición y el tamaño exactos de cada caja, en cascada desde la raíz y en función del viewport. Cambiar dimensiones, márgenes, tipografía o insertar nodos obliga a recalcular este nodo y, casi siempre, a sus vecinos y ancestros. Es la etapa más cara.

Paint y composite · píxeles y capas

Paint rellena píxeles: color, texto, bordes, sombras, en una o varias capas. Composite ensambla esas capas en la imagen final; puede correr en la GPU y en un hilo aparte. transform y opacity solo tocan composite: no recalculan geometría ni repintan.

por qué importaAnimar propiedades de composite se hace en el hilo del compositor y sigue a 60 fps aunque el hilo principal esté ocupado con JavaScript.

Hilo principal vs hilo compositor

El hilo principal hace parseo, ejecución de JS, layout y paint: una sola cola. Si una tarea de JS tarda 300 ms, durante 300 ms no hay respuesta a clics ni layout. El hilo compositor mueve capas ya pintadas (scroll, animaciones de transform) sin depender del principal.

Critical rendering path

La secuencia mínima para el primer pixel útil: HTML → DOM, CSS → CSSOM, render tree, layout, paint. Optimizarla es reducir el número de recursos que bloquean, su tamaño y mejorar su orden de llegada. Todo lo demás (imágenes below-the-fold, JS de interacción) puede esperar.

Layout thrashing

Leer una propiedad geométrica (offsetHeight, getBoundingClientRect()) justo después de escribir estilos fuerza al navegador a hacer layout de inmediato para darte un valor correcto. Hazlo dentro de un bucle y provocas decenas de reflows sincrónicos por frame. Agrupa todas las lecturas primero y luego todas las escrituras.

02

Dónde se genera el HTML

La misma página se puede armar en el navegador, en el servidor por petición, en el build, o por trozos. Cada modelo mueve el trabajo a otro momento y cambia qué ve el usuario mientras espera.

CSR · client-side rendering · la SPA clásica

El servidor manda un HTML casi vacío y un bundle de JavaScript; el navegador construye la interfaz al ejecutarlo. Hasta que ese JS descarga, parsea y corre, la pantalla está en blanco. Resuelve el desarrollo de apps muy interactivas con una sola base de código, pero el TTI llega tarde y el HTML no sirve para buscadores ni para compartir.

SSR · server-side rendering

El servidor ejecuta el framework por cada petición y devuelve el HTML ya con contenido. El usuario ve algo útil antes de que el JS cargue (el LCP llega temprano), a cambio de un TTFB más alto y de gastar CPU del servidor en cada request. Sigue necesitando hidratación para volverse interactivo.

por qué importaEs la opción por defecto cuando el contenido es dinámico o personalizado y además tiene que indexarse.

SSG · static site generation

El HTML se genera una vez, en el build, y se sirve como archivo estático desde una CDN. TTFB mínimo, escala sin esfuerzo, casi sin costo de servidor. El límite: si algo cambia hay que reconstruir, y un sitio de 100 000 páginas tarda en compilar.

ISR · incremental static regeneration

SSG con fecha de caducidad: la página estática se sirve desde la CDN y se regenera en segundo plano cuando pasa su intervalo de revalidación o se dispara un webhook. Da la velocidad del estático a catálogos grandes que cambian a ritmo moderado, sin reconstruir todo el sitio.

Streaming SSR y React Server Components

El servidor envía primero un shell (cabecera, layout, esqueletos) y va enviando el resto del HTML en trozos a medida que los datos están listos; el navegador los pinta al llegar. Con RSC, algunos componentes se renderizan solo en el servidor y nunca mandan su JS al cliente. Resuelve el caso de una página cuyos datos lentos bloqueaban todo lo demás.

El costo del JavaScript

Un megabyte de JS no cuesta lo mismo que un megabyte de imagen. La imagen se decodifica fuera del hilo principal; el JS hay que descargarlo, parsearlo, compilarlo y ejecutarlo, y todo eso ocurre en el hilo principal, compitiendo con la interacción del usuario. Por eso el modelo de render se elige mirando cuánto JS obliga a enviar, no solo el TTFB.

Prerender parcial · shell estático + huecos dinámicos

El caso incómodo: una página de producto es casi toda cacheable (fotos, descripción, reseñas) salvo dos datos —el stock y el precio con el descuento del usuario. Con SSR entera pagas render por petición por el 5 % que cambia; con SSG no puedes mostrar el stock real. El prerender parcial genera en el build el HTML estático de todo lo que no cambia y deja agujeros marcados que se rellenan por streaming en cada petición. El usuario recibe al instante el shell desde la CDN y ve llegar los trozos dinámicos un momento después. Es la misma idea del streaming SSR llevada al límite: la frontera estático/dinámico deja de ser "la página" y pasa a ser "la región del árbol".

por qué importaEvita la falsa elección entre "todo estático" y "todo por request" en páginas que son mayormente lo primero con un par de datos de lo segundo.

Dónde corre el servidor: origen, región y edge

"SSR" no dice dónde. En el origen (un servidor Node en una región): acceso normal a la base de datos, sin límites raros, pero un usuario en otro continente suma la latencia de ida y vuelta a esa región. En el edge (cientos de ubicaciones cerca del usuario): TTFB bajísimo y geolocalización barata, a cambio de un runtime recortado (sin APIs de Node completas, límites de CPU y de tamaño) y de que tu base de datos sigue en una región —una consulta desde el edge puede ser más lenta que desde el origen. Regla habitual: edge para middleware, redirecciones, A/B testing y personalización ligera; origen para lo que habla mucho con la base de datos.

03

Estado y reactividad

Casi todo bug de interfaz es un problema de estado: dónde vive, quién lo puede cambiar y cómo se entera la vista. Antes de elegir una librería, hay que saber qué tipo de estado se está guardando.

LOS CUATRO TIPOS DE ESTADO

Estado local · del componente

Un valor que solo le importa a un componente: si un menú está abierto, el texto de un input sin enviar. Vive en useState (o equivalente) y se pierde al desmontar. Se comparte hacia abajo por props.

Estado de servidor · cache de datos remotos

Los datos que en realidad son del backend y el cliente solo tiene prestados: la lista de pedidos, el perfil del usuario. No es "estado" en sentido estricto, es una cache. Librerías como React Query o SWR gestionan por ti la clave, la revalidación, el estado de carga y error, y el deduplicado de peticiones. Tratarlo como estado local lleva a datos rancios y a refetch manual en todas partes.

por qué importaSeparar la cache de servidor del estado de UI elimina la mayoría del "estado global" que la gente cree necesitar.

Estado en la URL · la fuente compartible

Filtros, pestaña activa, término de búsqueda, paginación: si quieres que un enlace copiado reproduzca la misma vista, ese estado va en la query string o en la ruta. Sobrevive a la recarga y al botón atrás. Guardarlo solo en memoria rompe el compartir y la navegación.

Estado global · contexto o store

Lo que muchos componentes lejanos necesitan leer y escribir: tema, sesión, carrito. Vive en un contexto o en un store (Zustand, Redux, signals globales). Úsalo solo cuando pasar props se vuelve absurdo, porque todo lo que toca el store se vuelve candidato a re-render.

CÓMO SABE EL FRAMEWORK QUÉ REDIBUJAR

VDOM + diffing · React, versiones previas de Vue

Al cambiar el estado, el framework vuelve a ejecutar la función del componente, produce un árbol virtual nuevo, lo compara con el anterior y aplica al DOM real solo la diferencia. Es predecible pero re-ejecuta componentes enteros aunque cambie un dato pequeño.

Signals · Solid, Svelte 5, Vue 3, Angular

Un valor reactivo sabe exactamente qué partes de la vista lo leyeron. Al cambiar, actualiza solo esos nodos del DOM, sin re-ejecutar el componente ni hacer diff. Más eficiente por defecto, a cambio de un modelo mental distinto sobre cuándo se lee un valor.

Dirty checking · AngularJS histórico

Tras cada evento, el framework recorre todos los datos observados y compara con el valor anterior para ver qué cambió. Simple de entender, caro cuando la lista de cosas a vigilar crece.

Derivar > sincronizar

Si un valor se puede calcular a partir de otro (el total a partir de los ítems, el "hay errores" a partir de la lista de errores), calcúlalo en el render. No lo guardes en otro estado que hay que mantener en sincronía: esa sincronización es una fuente inagotable de bugs de "se quedó con el valor viejo".

El objeto inline como prop

Pasar style={{ margin: 8 }} o onClick={() => f()} crea un objeto o función nueva en cada render. Para el diffing es una referencia distinta cada vez, así que el hijo memoizado se vuelve a renderizar igual. Con muchos hijos, eso es una lista entera repintándose por nada. Se estabiliza con useMemo/useCallback o sacando el objeto fuera del componente.

Formularios: controlados vs no controlados

Un input controlado tiene su value atado al estado del framework: cada tecla dispara un render y el estado es la única fuente de verdad. Necesario cuando la UI tiene que reaccionar a cada tecla (validación en vivo, contador de caracteres, formatear un teléfono a medida que se escribe). Un input no controlado deja que el DOM guarde su propio valor y lo lees al enviar (por ref o FormData): cero renders por tecla, más simple, y es lo que hacen por debajo las librerías de formularios modernas para no repintar el formulario entero en cada pulsación. La validación se hace en el envío o al salir del campo (blur), no en cada tecla, y —esto es lo que se olvida— se repite en el servidor: la del cliente es cortesía para el usuario, no una barrera de seguridad.

por qué importaHacer todo controlado por defecto es la causa número uno de formularios lentos: un formulario de treinta campos que se re-renderiza completo con cada carácter.

Optimistic UI

Al dar "me gusta", la interfaz pinta el corazón lleno y sube el contador antes de que el servidor responda, asumiendo que va a salir bien. Si sale bien, ya está; si falla, se revierte al estado anterior y se avisa. Hace que acciones de latencia media se sientan instantáneas. Requiere: guardar el estado previo para poder deshacer, una clave estable para no duplicar si el usuario repite, y decidir qué operaciones lo merecen —un "me gusta" sí, un "transferir dinero" no. Las librerías de estado de servidor traen primitivas para esto (mutación optimista con rollback automático al error).

04

Hidratación y sus alternativas

Cuando el HTML llega renderizado desde el servidor, sigue siendo texto muerto: no responde a clics. Hidratar es el paso que lo vuelve interactivo, y es más caro de lo que parece.

Qué es hidratar

El navegador ya pintó el HTML del servidor. Ahora descarga el JS del framework, vuelve a construir el árbol de componentes en memoria, lo empareja con el DOM existente, adjunta los listeners de eventos y reconstruye el estado inicial. Recién entonces la página responde.

El costo: el árbol se construye dos veces

El servidor ya hizo el trabajo de renderizar, y el cliente lo repite entero solo para "engancharse" al HTML. En full hydration ese trabajo es proporcional a toda la página, no a la parte interactiva, y ocurre en el hilo principal.

por qué importaCuanto más grande la página, más tarda en volverse usable, aunque el 90% sea contenido estático que nunca necesitaba JS.

Uncanny valley · se ve listo, no lo está

Entre que el HTML se pinta y que termina la hidratación, la página parece completamente funcional pero ignora los clics. El usuario pulsa un botón, no pasa nada, vuelve a pulsar. Es peor que una pantalla de carga honesta porque rompe la expectativa.

Islands · Astro, Fresh

La página es HTML estático salvo componentes concretos marcados como interactivos (un carrusel, un buscador). Solo esas "islas" reciben JS y se hidratan; el resto nunca bloquea. El costo: decidir qué es isla y que las islas no comparten estado con facilidad.

Hidratación parcial y progresiva

Se envía todo el JS pero se hidrata por prioridad: primero lo visible o lo que el usuario está por tocar, después el resto, en ratos libres del hilo principal. Mejora la latencia del primer input sin cambiar el modelo de la app.

Resumability · Qwik

En vez de rehacer el árbol en el cliente, el servidor serializa todo el estado y los handlers dentro del HTML. El cliente arranca con casi cero JS y solo descarga el código de un handler cuando de verdad se interactúa con él. TTI teórico inmejorable, a cambio de un modelo mental nuevo y de serializar mucho en el HTML.

RSC · componentes que nunca hidratan

Los React Server Components se renderizan solo en el servidor y no envían su JS al cliente. Los componentes de cliente siguen hidratando; los de servidor son, en la práctica, HTML con datos. La frontera servidor/cliente pasa a ser una decisión de arquitectura.

Error de hidratación · el HTML del servidor no coincide con el del cliente

Al hidratar, el framework espera encontrar en el DOM exactamente el árbol que él acaba de generar en memoria. Si no coincide —el servidor pintó una fecha con su zona horaria y el cliente con otra, se usó Math.random() o Date.now() en el render, se leyó window o localStorage que en el servidor no existen, o hay HTML inválido como un <div> dentro de un <p> que el navegador "arregla"— el framework avisa y, según el caso, descarta el HTML del servidor y vuelve a renderizar en cliente, perdiendo la ventaja del SSR justo en esa parte.

por qué importaEs de los bugs más comunes al pasar de CSR a SSR y a veces solo se nota como un parpadeo o un salto de layout. El arreglo: no usar valores no deterministas en el render, aplazar lo que depende del navegador a un efecto tras el montaje, y validar el HTML.

05

Módulos, bundling y carga

El código se escribe en cientos de archivos y el navegador tiene que recibir unos pocos, en el orden correcto, cacheables. Entre medio hay un compilador que decide qué va en cada paquete.

De módulos a bundle

El bundler parte de un punto de entrada, sigue cada import, arma el grafo de dependencias y lo empaqueta en archivos que el navegador puede pedir. Sin esto tendrías cientos de peticiones en cascada, cada una esperando a la anterior.

Tree-shaking · requiere ESM

Eliminar del bundle el código que nadie importa. Solo funciona con módulos ES (import/export estáticos), porque el bundler necesita saber en tiempo de compilación qué se usa. Con require() dinámico de CommonJS no puede, y se lleva todo.

Code-splitting · lazy + Suspense

Cortar el bundle en trozos que se cargan cuando hacen falta: por ruta (cada página su chunk) o por componente (import() dinámico dentro de un <Suspense> para un modal o un editor pesado). El usuario no baja el código de páginas que no visita.

por qué importaEs la palanca más directa sobre el TTI: menos JS en la carga inicial, menos tiempo de parseo y ejecución en el hilo principal.

HTTP caching · hash de contenido + immutable

Cada chunk se nombra con un hash de su contenido (app.9f3a1c.js). Si el contenido no cambia, la URL no cambia y el navegador lo sirve de cache con Cache-Control: immutable, sin siquiera revalidar. Si cambia, cambia la URL y se descarga solo ese chunk. Por eso conviene separar el código que cambia poco del que cambia en cada deploy.

preload y prefetch

preload le dice al navegador que un recurso de esta página es urgente y lo suba ya (la fuente, el chunk de la ruta actual). prefetch baja en segundo plano, con baja prioridad, algo que probablemente haga falta después (el chunk de la ruta a la que el usuario va a navegar).

El costo real de una dependencia

No es solo los kilobytes: es descargar, parsear y ejecutar. Una librería de fechas completa para formatear una fecha, o toda una librería de utilidades para usar dos funciones, infla el bundle y el tiempo de arranque. Mide antes de añadir, y prefiere módulos que se puedan tree-shakear.

Por qué los bundlers nuevos son rápidos

esbuild (Go) y Turbopack o el núcleo de Vite (Rust) están escritos en lenguajes compilados con paralelismo real, frente a las herramientas antiguas en JavaScript de un solo hilo. Vite además, en desarrollo, no hace bundle: sirve módulos ES nativos al navegador y solo transpila el archivo que pides. Menos trabajo y en paralelo.

Módulos duplicados y el tamaño real del bundle

Dos dependencias que usan versiones distintas de una tercera (dos versiones de la librería de fechas, dos de un cliente HTTP) se empaquetan las dos: el bundle carga código repetido que nadie pidió. Se detecta con un analizador visual del bundle (treemap de qué ocupa cada módulo) y se arregla alineando versiones o con dedupe. Mirar ese treemap tras cada cambio grande de dependencias es la forma más barata de no despertar un día con 400 KB extra sin saber de dónde salieron.

Content Security Policy y el front

Una CSP es una cabecera (Content-Security-Policy) que le dice al navegador de qué orígenes puede cargar scripts, estilos, imágenes y a dónde puede conectarse. Bien hecha, un XSS que logre inyectar un <script> no se ejecuta porque su origen no está permitido. Impacta al bundling: no puedes usar eval ni new Function (algunos modos de dev de los bundlers los usan), los estilos y scripts en línea necesitan un nonce o un hash que el servidor inyecta en cada respuesta, y todo CDN de terceros hay que listarlo explícitamente. Empezar el proyecto con una CSP en modo report-only cuesta poco; añadirla a una app madura llena de scripts inline es semanas de trabajo.

CSS a escala

El CSS de una página pequeña es trivial; el de un producto con años encima es donde se pierde el control. El problema no es la sintaxis, es que todo es global y el orden importa.

EL MODELO

Cascada, especificidad, herencia

Cuando varias reglas afectan al mismo elemento, gana una según: origen e importancia, luego especificidad (un id pesa más que una clase, una clase más que un tipo), y a igualdad, la que aparece más tarde en la hoja. La herencia es aparte: algunas propiedades (color, font) pasan del padre al hijo si no se declaran.

El problema de escala

Todo selector es global. Dos personas llaman .card a cosas distintas y colisionan. Nadie se atreve a borrar una regla por miedo a romper algo lejano, así que el archivo solo crece (dead CSS). Y como el orden decide, mover un import cambia el aspecto de páginas que nadie tocó.

por qué importaCada enfoque moderno de CSS existe para atacar una de estas tres cosas: colisión, código muerto o dependencia del orden.

ENFOQUES

BEM · convención de nombres

.bloque__elemento--modificador. Evita colisiones por disciplina humana, no por herramienta: si alguien no la sigue, vuelve el problema. Cero costo en runtime.

Utility-first · Tailwind

Clases atómicas de un solo propósito (flex, pt-4) compuestas en el HTML. Colisión imposible, el compilador purga lo no usado, CSS final pequeño y estable. El costo: el marcado se llena de clases y la curva inicial es real.

CSS Modules

Escribes CSS normal en un archivo .module.css; el build renombra cada clase con un hash único por archivo. Scope local sin cambiar de lenguaje, sin runtime. El dead code se detecta por archivo, no regla a regla.

CSS-in-JS · runtime vs zero-runtime

Estilos co-locados con el componente en JS. En runtime (styled-components) la librería serializa e inyecta reglas al renderizar: comodidad a cambio de trabajo en cada render. En zero-runtime (vanilla-extract, Linaria) los estilos se extraen a un .css estático en el build: misma co-locación, sin costo en el cliente.

Estilos scoped · Vue, Svelte

El compilador del componente añade un atributo único a sus elementos y acota cada selector a ese atributo. Scope automático dentro del archivo de componente, costo mínimo.

HERRAMIENTAS DE CONTROL

Contención contain, content-visibility

contain le promete al navegador que lo que pasa dentro de un elemento no afecta al layout de fuera, así puede saltarse esa subárbol al recalcular. content-visibility: auto le dice que no gaste render en lo que está fuera de pantalla hasta que se acerque.

Capas de cascada @layer

Permite declarar el orden de prioridad entre grupos de estilos (reset, framework, componentes, utilidades) de forma explícita, en vez de depender del orden de los archivos o de subir la especificidad para ganar. Domestica el "quién gana".

Container queries

Aplicar estilos según el ancho del contenedor del componente, no del viewport. Un mismo componente de tarjeta se adapta igual esté en una barra lateral estrecha o en una rejilla ancha, sin saber nada de la página. Es lo que las media queries no podían hacer.

Accesibilidad

El navegador construye, junto al DOM, un segundo árbol que describe la página a las tecnologías de asistencia. Programar para accesibilidad es programar ese árbol, y casi siempre el HTML correcto ya lo hace bien.

El árbol de accesibilidad · paralelo al DOM

Por cada nodo relevante del DOM, el navegador expone un objeto con su rol (qué es), su nombre (cómo se llama), su estado (marcado, expandido, deshabilitado) y sus propiedades. El lector de pantalla no ve tu CSS: lee este árbol a través de la API de accesibilidad del sistema operativo.

HTML semántico primero

Un <button> ya trae rol de botón, foco con el tabulador, activación con Enter y Espacio, y estado deshabilitado. Un <div onclick> no trae nada de eso: para un lector de pantalla es texto, no un control. Reconstruir todo eso a mano es trabajo y casi siempre queda peor.

por qué importaLa mayoría de los problemas de accesibilidad se resuelven eligiendo el elemento correcto, antes de tocar ARIA.

ARIA · roles, estados, propiedades

Atributos que ajustan lo que el elemento comunica al árbol de accesibilidad cuando el HTML no alcanza (widgets complejos: tablist, combobox). ARIA no añade comportamiento: role="button" no hace que responda a Enter, eso lo pones tú. Y un ARIA mal puesto miente al usuario.

Foco · orden, trampa, visibilidad

El orden de tabulación sigue el orden del DOM: si lo reordenas visualmente con CSS, el foco se vuelve caótico. En un modal el foco debe quedar atrapado dentro mientras está abierto y volver al disparador al cerrar. :focus-visible muestra el anillo de foco al navegar con teclado y no al hacer clic. Un skip link deja saltar la navegación repetida.

Contraste · WCAG AA

El texto normal necesita una relación de contraste de al menos 4.5:1 con su fondo; el texto grande (a partir de 18.66 px en negrita o 24 px normal) y los elementos de interfaz, al menos 3:1. El gris claro sobre blanco es la falla más común, y afecta a cualquiera bajo el sol, no solo a personas con baja visión.

Teclado completo y lectores de pantalla

Todo lo que se hace con ratón se tiene que poder hacer con teclado: Tab para moverse, Enter y Espacio para activar, Escape para cerrar, flechas dentro de un grupo. El lector de pantalla narra el elemento enfocado leyendo rol, nombre y estado ("Enviar, botón"; "Aceptar términos, casilla, no marcada").

prefers-reduced-motion

Media query que expone la preferencia del sistema de reducir movimiento. Animaciones grandes, parallax y transiciones bruscas pueden causar mareo y náusea a personas con trastornos vestibulares. Respetarla es cambiar esas animaciones por un fundido corto o quitarlas.

Primera regla de ARIA: no usar ARIA

Si existe un elemento HTML nativo con la semántica y el comportamiento que necesitas, úsalo en vez de recrearlo con un <div> y atributos ARIA. Un ARIA incorrecto (un role que no corresponde, un aria-hidden sobre algo enfocable) deja al usuario de lector de pantalla peor que si no hubiera nada: le describe una interfaz que no existe. No ARIA es mejor que ARIA mal.

Formularios accesibles

Cada campo necesita un <label> asociado por for/id (o envolviendo al input): un placeholder no es una etiqueta —desaparece al escribir y suele fallar el contraste. El mensaje de error se enlaza con aria-describedby apuntando al id del texto de error, y el campo se marca aria-invalid="true"; así el lector de pantalla narra "Correo, edición, no válido, el correo no tiene arroba" al enfocar. Los campos obligatorios llevan required. Al enviar con errores, el foco se mueve al primer campo fallido o a un resumen de errores enlazado a cada campo.

Anuncios dinámicos aria-live

El lector de pantalla narra lo que está enfocado; no se entera de que apareció un toast, de que la búsqueda ya trae 12 resultados o de que se guardó el borrador. Una región en vivo (aria-live="polite" para lo no urgente, "assertive" para lo que interrumpe, o roles como status y alert) hace que el navegador anuncie los cambios de su contenido. Truco de implementación: el contenedor con aria-live tiene que existir en el DOM antes de meterle texto —si lo creas y lo rellenas a la vez, muchos lectores no lo anuncian.

Rendimiento percibido

El rendimiento que importa no es un número de laboratorio, es lo que siente un usuario real en su móvil de gama media. Google lo resume en tres métricas y las usa para rankear.

Core Web Vitals · LCP, INP, CLS

LCP (Largest Contentful Paint): cuánto tarda en pintarse el elemento más grande del viewport; bueno por debajo de 2.5 s. INP (Interaction to Next Paint): la latencia de la interacción más lenta de toda la visita; bueno por debajo de 200 ms. Reemplazó a FID como métrica oficial en marzo de 2024 por medir toda la visita y no solo el primer input. CLS (Cumulative Layout Shift): cuánto se mueve el contenido de forma inesperada; bueno por debajo de 0.1.

Imágenes · suelen ser el LCP y el CLS

Formatos modernos (AVIF, luego WebP, con JPEG de reserva) pesan bastante menos. srcset deja al navegador elegir la resolución según pantalla. loading="lazy" difiere las de abajo del pliegue. Y siempre ancho y alto explícitos (o aspect-ratio): sin eso, la imagen empuja el texto al cargar y dispara el CLS.

por qué importaLa imagen hero suele ser el elemento LCP; optimizarla mueve la métrica más que cualquier otra cosa.

Fuentes · FOUT vs FOIT

Mientras la fuente web carga, el navegador o muestra texto con una fuente de sistema y luego cambia (FOUT, flash of unstyled text) o no muestra texto (FOIT, flash of invisible text). font-display controla cuál: swap prioriza ver texto, optional evita el salto tardío. Ayuda además hacer subset (solo los caracteres que usas) y preload de la fuente principal.

Skeleton vs spinner

Un spinner dice "algo pasa" sin más; un skeleton dibuja la forma del contenido que viene y hace la espera más corta en la percepción, además de reservar el espacio y evitar el salto de layout. La misma latencia se siente distinta según qué muestres durante la espera.

Percepción > números

Mostrar el shell de inmediato, cargar primero lo visible, dar feedback instantáneo al clic aunque la respuesta tarde: todo eso mejora la experiencia sin cambiar el tiempo total. El usuario no cronometra, recuerda si se sintió rápido.

RUM vs lab

Lab (Lighthouse, WebPageTest): entorno controlado, reproducible, bueno para depurar y para no regresionar. RUM (Real User Monitoring, el Chrome UX Report): datos de usuarios reales con sus redes y dispositivos, que es lo que Google usa para rankear. El lab te dice por qué; el RUM te dice si de verdad pasa.

Tareas largas y ceder el hilo · la palanca de INP

Cualquier bloque de JavaScript que ocupe el hilo principal más de 50 ms es una long task: mientras corre, el navegador no puede responder a un clic ni pintar. Si el usuario interactúa justo entonces, ese retraso entra en el INP. Arreglos: partir el trabajo en trozos y ceder el hilo entre ellos (await scheduler.yield() donde esté disponible, o setTimeout(0) / postTask como alternativa), mover el cálculo pesado a un web worker, y aplazar lo que no es urgente con requestIdleCallback. Medir una interacción real en el perfil de DevTools muestra exactamente qué función la bloqueó.

Scripts de terceros

Analítica, chat de soporte, píxeles de publicidad, gestores de consentimiento: código que no escribiste, que se ejecuta en tu hilo principal y que suele ser la mayor causa de INP y LCP malos en sitios por lo demás cuidados. Defensa: cargarlos con async o diferidos, después de la interacción o cuando el navegador está ocioso; considerar ejecutarlos en un worker aislado; medir el coste de cada uno y quitar los que no ganan su peso; y no fiarse de "es solo un snippet", porque ese snippet a menudo carga otros scripts en cadena.

bfcache · back/forward instantáneo

Al pulsar "atrás", el navegador puede restaurar la página anterior entera desde memoria —DOM, JS, posición de scroll— en vez de recargarla: navegación instantánea y sin volver a pegar al servidor. Se pierde esta ventaja si la página usa unload, si manda Cache-Control: no-store, o si tiene una conexión abierta que impide congelarla. DevTools tiene una prueba de bfcache que dice por qué una página no es elegible. Recuperarla mejora la métrica de navegación para toda la gente que usa el botón atrás, que son muchos.

Prioridad de carga fetchpriority, preload, sizes

El navegador adivina la importancia de cada recurso, y a veces se equivoca: baja la imagen hero (que es el LCP) con la misma prioridad que un icono del pie. fetchpriority="high" en la imagen LCP y "low" en lo de abajo del pliegue corrige eso. <link rel="preload"> adelanta un recurso crítico que el navegador descubriría tarde (una fuente referida desde el CSS). Y en imágenes responsive, un atributo sizes mal puesto hace que el móvil baje la versión de escritorio: srcset ofrece los anchos, sizes le dice al navegador cuánto espacio ocupará la imagen para que elija bien antes de conocer el layout.

09

Testing de front-end

Un test de front-end vale por la confianza que da al hacer un cambio, no por el porcentaje de cobertura. Eso decide qué probar, con qué herramienta y en qué nivel: la mayor parte del esfuerzo va donde el usuario y el componente se encuentran, no en las funciones sueltas ni en los flujos de punta a punta.

QUÉ NIVEL PRUEBA QUÉ

Del "pirámide" al "trofeo" · Kent C. Dodds

La pirámide de tests clásica pone muchos tests unitarios en la base, menos de integración y unos pocos de punta a punta. En el front esa forma engaña: un componente aislado con todo mockeado puede pasar en verde mientras la pantalla real está rota, porque lo que falla suele estar en la costura entre piezas. El trofeo reordena por retorno de confianza: una base pequeña de análisis estático (tipos, linter), unos pocos unitarios para lógica pura compleja, el grueso en tests de integración de componentes que montan varias piezas juntas, y una capa fina de E2E para los caminos que no se pueden perder.

por qué importaEl coste de un test no es solo escribirlo: es mantenerlo cuando refactorizas. Los unitarios que espían la implementación se rompen en cada refactor sin haber encontrado un solo bug; los de integración sobreviven al refactor y fallan cuando de verdad algo dejó de funcionar.

La regla de oro · "prueba como lo usa el usuario"

Cuanto más se parezca el test a cómo se usa el software, más confianza da. En la práctica: el test no sabe que existe useState, no llama a métodos del componente, no comprueba props internas. Renderiza, busca elementos como los buscaría una persona ("el botón que dice Guardar"), interactúa y verifica lo que se ve. Si un refactor no cambia lo que el usuario percibe, el test no debería enterarse.

TESTS DE COMPONENTE CON TESTING LIBRARY

Queries: por rol y nombre accesible, primero

Testing Library ordena sus queries por preferencia. Arriba, las que cualquiera puede percibir: getByRole('button', { name: /guardar/i }), getByLabelText, getByText, getByPlaceholderText. Al fondo, como último recurso, getByTestId con un data-testid. Buscar por clase CSS ni siquiera es una opción de la API: la clase es un detalle de estilo que cambia sin que cambie la interfaz.

por qué importaSi tu componente no se puede encontrar por rol y nombre, un lector de pantalla tampoco lo encuentra. El test que insiste en queries accesibles empuja el marcado hacia la accesibilidad casi sin querer. El testid es para el nodo que de verdad no tiene semántica (un contenedor de layout) y que igual necesitas anclar.

userEvent vs fireEvent

fireEvent.click(node) dispara un evento de DOM y nada más. Una persona que hace clic genera antes pointerdown, mousedown, focus, pointerup, mouseup, click; al escribir dispara keydown, actualiza el valor, dispara input, respeta maxlength y el estado deshabilitado. userEvent simula esa secuencia completa, así que descubre bugs que fireEvent nunca toca (un handler que depende de focus, un input que ignora el evento sintético). Es asíncrono: se usa con await y conviene crear la instancia con userEvent.setup() antes de renderizar.

Esperar lo asíncrono sin sleep

Cuando algo aparece tras una petición o un estado que cambia, se usan findBy* (query + espera hasta que exista) y waitFor (reintenta una aserción hasta que pasa o expira). Nunca un setTimeout fijo: en CI la máquina va más lenta y el número mágico que funcionaba en tu portátil falla una de cada veinte veces. act() envuelve las actualizaciones de estado para que el árbol se estabilice antes de la aserción; la mayoría de las utilidades de Testing Library ya lo hacen por dentro.

El anti-patrón: testear la implementación

Señales de que un test está atado a los detalles internos y no al comportamiento: usa container.querySelector('.foo'), comprueba el estado con un wrapper tipo wrapper.state(), mockea un componente hijo para "aislar", o afirma que una función se llamó "una vez" cuando lo que importa es el efecto visible. Todos pasan en verde con la interfaz rota y fallan en rojo con la interfaz intacta. Regla práctica: si no puedes explicar el test sin nombrar una variable interna, está mal escrito.

MOCKS DE RED

MSW · interceptar a nivel de red

Mock Service Worker intercepta las peticiones HTTP donde salen —en el navegador con la Service Worker API, en Node con un interceptor de bajo nivel— en vez de sustituir fetch o axios con un doble. Defines handlers por endpoint (http.get('/api/pedidos', ...)) que devuelven respuestas simuladas. El código de la app no cambia ni sabe que está mockeado: usa su cliente HTTP real, su serialización real, sus reintentos reales.

por qué importaMockear el módulo (jest.mock('./api')) prueba tu código contra tu propia idea de la API; si el backend devuelve otra forma, el test sigue verde. Con MSW el mismo handler sirve para tests, para Storybook y para desarrollar sin backend, y migrar de una librería HTTP a otra no rompe ni un test.

E2E: PLAYWRIGHT Y CYPRESS

Qué probar de punta a punta y qué no

E2E arranca un navegador real contra la app desplegada y recorre un flujo entero: registrarse, añadir al carrito y pagar, recuperar la contraseña. Son lentos, caros en CI y más frágiles, así que se reservan para los caminos críticos de negocio —los que si se rompen pierdes dinero o usuarios— y para verificar la integración real (auth, pasarela de pago, redirecciones). No se usan para cubrir cada variante de un formulario ni cada estado de un componente: eso es trabajo de los tests de integración, mil veces más rápidos.

Flakiness y cómo matarla

Un test flaky pasa o falla sin que el código cambie, y envenena la suite entera porque la gente aprende a ignorar los rojos. Causas y arreglos: esperas fijas → usar el auto-waiting (Playwright espera a que el elemento sea visible, estable y accionable antes de actuar; sus web-first assertions reintentan solas). Selectores frágiles → localizar por rol y texto (getByRole), no por XPath ni por clases generadas. Estado compartido entre tests → cada test crea y limpia sus propios datos, aislado. Orden implícito → los tests no deben depender de correr en secuencia. Animaciones y tiempo real → desactivar animaciones y congelar el reloj. Como red de seguridad, no como cura: retries en CI y marcar y arreglar el test que reintenta.

Page objects y datos de prueba

El page object (o fixture en Playwright) encapsula los selectores y las acciones de una pantalla —loginPage.submit(user, pass)— para que un cambio de marcado se arregle en un sitio y no en cuarenta tests. Los datos de prueba no se pinchan a mano en la UI: se siembran por API o por base de datos antes del test (más rápido y fiable) y se limpian después; el usuario de prueba se crea por test o por worker para poder correr en paralelo sin pisarse.

MÁS ALLÁ DEL DOM

Visual regression

Los tests de DOM no ven que un margen se rompió o que el texto quedó blanco sobre blanco. La regresión visual toma una captura de cada componente o página, la compara pixel a pixel con la aprobada y falla si difieren más de un umbral. Chromatic (integrado con Storybook), Percy o las propias toHaveScreenshot de Playwright. El coste: mantenimiento de las baselines y falsos positivos por antialiasing o fuentes; se controla fijando el navegador, el viewport y desactivando animaciones, y revisando los diffs como se revisa un PR.

Accesibilidad automatizada y su límite

axe-core (vía jest-axe, el plugin de Playwright o el addon de Storybook) escanea el DOM renderizado y detecta violaciones comprobables por máquina: contraste insuficiente, img sin alt, campos sin etiqueta, id duplicados, orden de encabezados. Es barato y conviene tenerlo en cada test de componente. Su límite: cubre del orden de un tercio de los criterios de WCAG. No sabe si el alt describe bien la imagen, si el orden de foco tiene sentido, si un aria-label miente o si el flujo con teclado es usable. Eso sigue necesitando prueba manual con teclado y lector de pantalla.

Qué NO testear

La implementación (ya visto). Las librerías de terceros: no pruebas que React Router navega o que la librería de fechas formatea; asumes que su propia suite lo cubre y pruebas cómo tu código las usa. El código generado y los tipos. Los estilos exactos con aserciones sobre CSS (para eso está la regresión visual). Y no persigas el 100% de cobertura: la última franja suele ser getters triviales y ramas de error imposibles, y el tiempo rinde más escribiendo un test de integración que falte.

CI: shards, paralelización y retries

Una suite E2E de veinte minutos en serie bloquea los despliegues. Se parte en shards: N máquinas corren cada una una fracción de los tests (--shard=1/4) y el tiempo total baja casi lineal. Dentro de cada máquina, varios workers en paralelo (limitados por CPU). Los retries solo en CI, con tope de 1 o 2, y todo test que reintente se registra para arreglarlo —si no, la flakiness se vuelve permanente. El trace o vídeo se guarda solo del intento fallido, para depurar sin reproducir en local. Los tests de integración (miles, en Node) caben en un solo job de un par de minutos; los que hay que trocear son los E2E.

Orden de ejecución en el pipeline

Barato y rápido primero, para fallar pronto: typecheck y lint (segundos) → tests unitarios y de integración con MSW (minutos) → build → E2E y regresión visual contra el preview desplegado (más lentos, en shards). Si el typecheck falla no tiene sentido gastar diez minutos de E2E. Los tests de componente se pueden correr también dentro de Storybook con su runner, reutilizando las stories como casos.

Internacionalización y localización

Adaptar un producto a otro idioma casi nunca es "traducir los textos". Es que las fechas, los números, los plurales, la dirección de la escritura y hasta el ancho de un botón cambian de región en región, y que casi todo eso ya lo resuelve el navegador si no lo peleas.

i18n vs l10n · preparar vs traducir

Internacionalización (i18n) es el trabajo de ingeniería que se hace una vez: sacar todo el texto del código a archivos de mensajes, no concatenar cadenas, delegar los formatos, soportar escritura de derecha a izquierda, dejar que el layout respire cuando el texto crece. Localización (l10n) es lo que se hace por cada mercado: traducir esos mensajes, ajustar ejemplos y moneda, revisar imágenes y tono. Si la i18n está bien hecha, añadir un idioma es un archivo nuevo; si está mal, es refactorizar la app entera.

por qué importaEl coste de la i18n se paga entero la primera vez. Empezar "en un idioma y ya veremos" y meterla después significa tocar cada componente que muestra texto, fecha o número.

Intl nativo · no reinventes el formateo

El navegador trae la base de datos de locales de Unicode (CLDR) y la expone en el objeto Intl. Intl.DateTimeFormat da "9 de septiembre de 2026" o "September 9, 2026" o "2026年9月9日" según el locale, con su orden, sus separadores y su calendario. Intl.NumberFormat pone el separador de miles y decimales correcto (1.234,56 en español, 1,234.56 en inglés) y, con style: 'currency', coloca el símbolo donde va y con los decimales que esa moneda usa (el yen no lleva decimales). También hay RelativeTimeFormat ("hace 3 días"), ListFormat ("A, B y C"), Collator (ordenar respetando acentos y ñ) y PluralRules.

por qué importaFormatear a mano con replace y plantillas parece inocente y falla en el primer locale que no imaginaste: el que usa coma decimal, el que pone el símbolo de moneda detrás, el que separa los miles con un espacio fino. Intl ya lo sabe para ~cientos de locales y no pesa nada porque va en el motor.

Pluralización · no hay "singular y plural"

El inglés tiene 2 formas (1 vs resto); el chino y el japonés, 1 sola; el árabe, 6; el ruso y el polaco, 3 según la terminación del número. Un if (n === 1) produce texto agramatical en la mayoría de los idiomas del mundo. Intl.PluralRules devuelve la categoría (one, few, many, other…) y las librerías de i18n la usan bajo el capó. El formato estándar para esto es ICU MessageFormat, que mete la lógica dentro del propio mensaje — {n, plural, one {# archivo} other {# archivos}}— para que el traductor rellene las categorías que su idioma necesita sin tocar código.

Género, orden de palabras e interpolación

ICU MessageFormat también cubre select para género ({genero, select, female {ella} male {él} other {le}}) y, sobre todo, interpolación con posición libre: el traductor decide dónde caen las variables dentro de su frase. "Añadiste {producto} a {lista}" en otro idioma puede necesitar el orden inverso; si tu sistema concatena "Añadiste " + producto + " a " + lista ese idioma queda roto para siempre. El mensaje se entrega con marcadores nombrados ({producto}) y el motor los sustituye al final.

RTL · árabe, hebreo, persa, urdu

En estos idiomas la interfaz se refleja como en un espejo: el menú a la derecha, la flecha de "atrás" apunta a la derecha, el progreso avanza hacia la izquierda. Se activa con <html dir="rtl">, pero solo funciona si el CSS usa propiedades lógicas: margin-inline-start en vez de margin-left, padding-inline, inset-inline-end, text-align: start. Con propiedades físicas (left, right) hay que mantener dos hojas de estilo. Los iconos direccionales (flechas, "responder", lápiz de "editar" a veces) se espejan con transform: scaleX(-1) bajo [dir="rtl"]; los que no tienen dirección (una lupa, un corazón) se dejan igual. Los números y el código embebido siguen siendo LTR dentro del texto RTL: eso lo maneja el algoritmo bidireccional de Unicode, con ayuda de <bdi> para datos de usuario.

Extracción de strings y el flujo con traductores

Las cadenas viven en archivos de mensajes por idioma (es.json, ar.json…). Cada entrada tiene una clave. Dos escuelas: clave semántica (checkout.payButton) o el texto por defecto como clave ("Pagar ahora"). La primera aguanta cambios de redacción sin re-traducir; la segunda es más legible en el código y detecta huérfanos al instante. En cualquier caso, el traductor necesita contexto: un comentario que diga si "Post" es el sustantivo (publicación) o el verbo (publicar), dónde aparece, si hay límite de caracteres. Una herramienta de extracción recorre el código, saca las claves a un formato que la plataforma de traducción entiende, y marca lo nuevo y lo que quedó sin usar. Un pseudo-locale (acentos falsos y texto alargado un 40%) en CI destapa strings hardcodeados y layouts que no aguantan antes de encargar la traducción.

Carga de bundles por idioma

Un usuario necesita un idioma, no cuarenta. Los mensajes de cada locale se cargan por import() dinámico según el idioma resuelto, y solo ese archivo viaja al cliente. Los datos de Intl ya van en el navegador, así que no se empaquetan. En SSR, el servidor renderiza directamente en el idioma correcto (no un idioma y luego cambio en cliente, que causa parpadeo y CLS). Se precarga el locale por defecto y se difieren los demás.

Design systems y design tokens

Un design system no es una carpeta de componentes de React. Es el contrato compartido entre diseño y desarrollo —los valores, los nombres, las reglas de uso y la manera de versionarlos— que hace que dos personas construyendo dos pantallas distintas produzcan algo que parece el mismo producto.

Qué es un design system de verdad

Cuatro capas, y la librería de componentes es solo una: (1) fundamentos — color, tipografía, espaciado, radios, sombras, movimiento— expresados como valores nombrados; (2) componentes — la implementación de botón, campo, modal, con sus estados y su marcado accesible; (3) guías de uso — cuándo va un botón primario y cuándo uno secundario, qué tono usa un mensaje de error, cómo se escribe un placeholder; (4) gobernanza — quién decide, cómo se propone un cambio, cómo se publica y se comunica. Sin (3) y (4), un equipo grande diverge en meses aunque tenga los componentes.

por qué importaLos proyectos que "montan un design system" y solo hacen la librería de componentes acaban con veinte tonos de gris y cuatro estilos de botón igualmente, porque nada impedía inventárselos.

Design tokens · los valores con nombre

Un token es un par nombre → valor que sustituye a los números mágicos del CSS. color-blue-600 = #1d4ed8. Se declaran una vez, en un formato neutral, y una herramienta los transforma a lo que cada plataforma necesita: custom properties de CSS, constantes de JS, XML de Android, un archivo de iOS. Cambiar el azul de marca es cambiar un token y republicar, no un find-and-replace por cientos de archivos.

Las tres capas: primitivo → semántico → de componente

Primitivos (o "globales"): la paleta cruda, sin significado — blue-100 … blue-900, space-1 … space-12. Nadie los usa directo en un componente. Semánticos (o "de alias"): le dan intención — color-bg-surface, color-text-danger, color-border-focus, space-inset-md. Apuntan a un primitivo. De componente: el más específico, opcional — button-primary-bg, input-border-invalid— y apunta a un semántico. La regla: un componente consume tokens semánticos o de componente, nunca primitivos.

por qué importaEsta indirección es lo que hace posible el tema oscuro y los temas de marca sin tocar un solo componente: se cambia a qué primitivo apunta cada semántico y todo se recolorea.

El formato estándar: W3C / DTCG

El Design Tokens Community Group del W3C publicó su primera versión estable en octubre de 2025. Define una forma común: un token es un objeto con $value y $type (color, dimension, fontFamily, duration…), y un token puede referenciar a otro por su ruta ("$value": "{color.blue.600}") — que es justo lo que permite la capa semántica. Con ese formato, Figma, Tokens Studio, Style Dictionary, Terrazzo y otras herramientas leen y escriben el mismo archivo, así que un token definido una vez viaja entre diseño y código sin un exportador a medida por cada destino.

Temas como remapeo de tokens semánticos

Claro/oscuro, marca A/marca B, densidad cómoda/compacta: cada tema es un conjunto de valores para los mismos tokens semánticos. En CSS suele implementarse con custom properties redefinidas bajo un selector (:root, [data-theme="dark"], @media (prefers-color-scheme)). El componente escribe background: var(--color-bg-surface) y no sabe ni le importa en qué tema está. Añadir un tercer tema es una hoja de valores nueva, cero cambios en componentes.

Storybook · catálogo vivo

Storybook renderiza cada componente aislado, en todos sus estados, fuera de la app. Cada story es una combinación de props ("Botón / primario / cargando"). Sirve tres propósitos a la vez: documentación que no se desactualiza porque es el componente real; banco de pruebas visual mientras lo construyes, sin navegar por la app hasta el estado que te interesa; y fixtures de test — las mismas stories las consumen la regresión visual, los tests de interacción (el play function ejecuta clics y aserciones) y el escaneo de accesibilidad. Addons habituales: el de a11y (axe sobre cada story), controls (editar props en vivo), interactions (paso a paso del play function). Storybook 9 (2025) integró ese testing con Vitest y adelgazó bastante el paquete.

El contrato con diseño

El design system funciona cuando diseño y código comparten vocabulario: si en Figma la variable se llama bg/surface/raised y en el código color-bg-surface-raised, una conversación sobre "el fondo de las tarjetas" no necesita traducción. Las Figma variables mapean casi uno a uno con los tokens DTCG, y hay flujos que sincronizan en ambos sentidos. Falta acordar quién es dueño de qué: normalmente diseño posee los valores de los tokens y las guías de uso; desarrollo posee la implementación, la API de los componentes y la accesibilidad; y los cambios que cruzan la frontera (un token nuevo, un componente nuevo) pasan por una propuesta que ambos revisan.

Versionado, publicación y migraciones

El design system se distribuye como uno o varios paquetes con versionado semántico. Un cambio que rompe la API de un componente o renombra un token es major y llega con changelog y, si se puede, un codemod que actualiza el código consumidor automáticamente. Los tokens se publican también como paquete para que un rebranding se propague por npm update. Sin esta disciplina, cada equipo fija su versión, deja de actualizar y a los seis meses hay cinco versiones del sistema conviviendo, que es peor que no tener sistema.

Cuándo NO construir uno propio

Un design system completo es un producto con equipo dedicado, roadmap y mantenimiento indefinido. Para la mayoría de proyectos —un equipo, un producto, sin necesidad de identidad visual única— la respuesta es partir de primitivas de comportamiento sin estilo (Radix UI, React Aria, Ark) o de un kit ya montado sobre ellas (shadcn/ui, que copias a tu repo y modificas), y definir solo tu capa de tokens encima. Construir botón, combobox, date picker y dialog accesibles desde cero cuesta meses y sale peor que lo que ya existe probado. Un design system propio se justifica cuando hay varios productos que compartir, una marca que expresar con precisión, o una plataforma (móvil + web + terceros) que unificar.

por qué importaEl error caro no es elegir mal la librería, es decidir construir la base entera cuando el problema real eran cinco componentes y una paleta.

Un design system sin gobernanza es documentación que envejece.
